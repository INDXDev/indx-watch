目的

コードの変更とテスト結果を結びつける。エンジニアは PR の画面から結果を見られ、QA はどのデプロイに対してテストしたかを取り違えない。

注記

  1. 1GitHub App の接続状態。未接続・権限不足のときは管理者向けに設定手順を表示。
  2. 2deployments の新しい順。自動テスト列は、そのデプロイメントに紐づく runs の集計。
  3. 3変更ファイルは GitHub API から取得してキャッシュ（D1 には保存しない）。
  4. 4影響分析は ai_suggestions（kind=impact）。変更ファイル・PR 説明・TC の手順と AC を突き合わせ、理由付きで TC を選ぶ。P0 のスモークは常に含める。
  5. 5Check Run 名は INDX Watch。needs_review があれば action_required、fail があれば failure、すべて pass で success。
  6. 6PR コメントは 1 件を上書き更新し、PR をコメントで埋めない。
  7. 7Issue には実行 ID・手順・期待結果・スクリーンショットへのリンク・判定理由を本文に入れる。issues に記録し、状態を同期。
  8. 8webhook 受信ログ。署名不一致は破棄して記録する。

表示データ

  • deployments: environment_id, commit_sha, ref, pr_number, release_id, url, source, status, deployed_at
  • runs: deployment_id ごとの verdict 集計
  • ai_suggestions: kind=impact の payload_json（選んだ TC と理由）
  • issues: run_id, external_id, url, state
  • activity_log: action = github.webhook（イベント種別・結果コード）

操作

  • デプロイメントを手動で登録（GitHub 以外からのデプロイ用）
  • 影響分析の結果に TC を追加 / 除外して再実行
  • Check Run を再送信、PR コメントを更新
  • 不合格の実行から Issue を作成
  • webhook の再処理（失敗したイベントのみ、admin）

AI の役割

  • PR の差分と説明から影響する TC を選ぶ（claude-sonnet-5-5）。理由を 1 行で残す。
  • Issue 本文の下書き（再現手順・期待と実際の差・証拠リンク）を作る。送信前に人が編集できる。
  • 影響分析で「対応する TC がない変更」を見つけたら、TC の追加を S10 の提案として出す。

この画面の完了条件

  • GitHub から deployment_status: success を受け取ると 10 秒以内に一覧へ行が追加される。
  • 署名（X-Hub-Signature-256）が不正な webhook は 401 を返し、データを変更しない。同じ delivery ID は二重処理しない。
  • PR の preview デプロイに対し、影響分析で選ばれた TC と P0 スモークが自動実行される。
  • 実行完了後、Check Run の結論が注記 5 のルール通りに GitHub に送られ、PR コメントは 1 件だけ存在する。
  • 不合格の実行から Issue を作ると、本文に実行 ID・手順・証拠リンクが入り、issues に記録される。
  • GitHub App 未接続のとき、手動登録だけで全機能（自動実行以外）が使える。
  • guest にはこの画面を表示しない。
