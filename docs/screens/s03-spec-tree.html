AI の指摘 網羅の質 4

AC-12.3 は「決済完了」と「メール到達」の 2 つを 1 つの TC で確かめています。メール判定が要確認になりやすいため、TC を分けることを提案します。また PR #482 で追加された「会員割引との併用不可」のルールに対応する AC がありません。

目的

仕様の全体像と「完了の定義」を 1 か所で管理する。AC を中心に、テストで確かめられていない部分を見える化する。

注記

  1. 1プロジェクト内で ready な TC に 1 件も紐づかない AC を常に上部に出す。0 件なら非表示。
  2. 2各ノードの右に AC 網羅（紐づく AC / 全 AC）と、選択中の判定基準での最悪状態の色。fail > blocked > 要確認 > 実行中 > 未実行 > pass の順に優先。
  3. 3AC ごとに検証する TC を表示。1 つの TC が複数 AC を検証してもよい（test_case_criteria は多対多）。draft の TC は点線枠で「未承認」表示し、網羅には数えない。
  4. 4AI の指摘は UC を開いたときに非同期で取得（キャッシュあり）。採用すると S10 と同じ承認フローで draft が作られる。

表示データ

  • features / use_cases（number・title・actor・goal・priority・origin）
  • acceptance_criteria（seq・text）
  • test_case_criteria → test_cases（status・mode・priority）
  • runs: 判定基準（リリースの最新デプロイ）での TC ごとの最新 verdict・信頼度
  • ai_suggestions（source に UC を含む pending）
  • activity_log: 「履歴」タブ

操作

  • ユースケース・AC の追加・編集・並べ替え（ドラッグ）。AC の文言変更は履歴に残し、紐づく TC の担当者に通知
  • AC 行から [テストケースを追加]（S04 の新規作成を AC 紐づけ済みで開く）
  • AI でテストケースを提案 → ai_suggestions（kind=tc_generate）を作成し S10 で承認
  • ドキュメントから取り込む → S10

AI の役割

  • AC の曖昧さ・抜け（エラー時・境界値・権限）を指摘
  • PR の差分や仕様書から、追加すべき AC と TC を提案
  • 提案はすべて draft。人の承認なしに網羅率は上がらない

この画面の完了条件

  • ツリーの網羅数とバッジ色が注記 2 のルールで計算され、S02 の値と一致する
  • AC を削除しようとしたとき、紐づく TC があれば件数を示して確認する（画面内の確認 UI）
  • AC の追加・文言変更・並べ替えが activity_log に差分つきで残る
  • draft の TC は網羅に数えず、承認した瞬間に網羅数が更新される
  • 500 UC の規模でツリーの初期表示が 1 秒以内（ツリーは集計済みクエリ 1 本）
  • URL の ?uc= で選択状態を共有できる
