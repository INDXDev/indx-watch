SPEC-02 · ドメインモデル

ドメインモデル・用語・状態遷移

INDX Watch に出てくる言葉の定義と、それぞれの関係、状態の変わり方、「完了」の決め方をまとめます。画面・API・テーブルはすべてこのページの言葉に合わせます。

状態 ドラフト v0.1更新 2026-11-19関連 データモデル · AI ネイティブ設計

全体像

中心にあるのは「仕様ツリー」と「実行」の 2 本です。仕様ツリーは 何ができれば完了か を表し、実行は 実際にどうだったか を証拠付きで記録します。両者をつなぐのがテスト計画（誰が・どこで・いつまでに）です。

flowchart LR
  subgraph SPEC["仕様ツリー（何ができれば完了か）"]
    F["機能 FEAT"] --> UC["ユースケース UC"]
    UC --> AC["完了条件 AC"]
    TC["テストケース TC"] -- 検証する --> AC
    TC --> TCV["TC バージョン"]
    TCV -- 使う --> FXV["フィクスチャ版 FX vN"]
  end
  subgraph WHERE["どこで"]
    P["プロジェクト = リポジトリ"] --> ENV["環境"]
    P --> REL["リリース"]
    REL --> DEP["デプロイメント = commit × 環境"]
  end
  subgraph PLAN["誰が・いつまでに"]
    PL["テスト計画 PLAN"] --> PI["計画アイテム（アサイン）"]
  end
  subgraph RUN["実際にどうだったか"]
    R["実行 RUN"] --> RS["ステップ結果"]
    RS --> EV["証拠"]
    R --> J["判定（ジャッジ）"]
    J --> V["最終判定 verdict"]
  end
  REL --> PL
  PI -- 対象 --> TC
  PI -- 実行 --> R
  R -- 使った版 --> TCV
  R -- 対象 --> DEP

優先度

ユースケースとテストケースに付けます。テストケースの優先度は、検証するユースケースの優先度を既定値として引き継ぎ、個別に変えられます。

優先度意味例リリース判定での扱い
P0壊れたらリリースできない。お金・ログイン・個人情報に関わる。決済、ログイン、注文確定全件合格が必須。要確認が 1 件でもあれば No-Go。
P1主要な導線。壊れると多くの人が困る。商品検索、クーポン適用合格率 95% 以上（既定）。不合格は既知の問題として承認が必要。
P2通常の機能。回避策がある。並び替え、お気に入り集計はするが判定条件には入れない（既定）。
P3細部・見た目。文言、余白同上。

実行モードとジャッジ

実行モード（テストケースごと）

manual
人が手順に沿って操作し、各ステップで合否を付ける。証拠はスクリーンショットを貼る。
agent
AI ブラウザエージェントが自然言語の手順を実行し、ジャッジが判定する。
script
Playwright スクリプトを Browser Run 上で実行する。最も速く安定。
hybrid
エージェントが実行し、人が証拠を見て最終判定する。P0 の既定。

ジャッジ（判定する仕組み）

assert
決定的なチェック。URL、テキストの有無、要素の状態、HTTP ステータス。
visual
承認済みベースライン画像との差分率。閾値を超えたら要確認。
llm
ルーブリックとスクリーンショット・DOM を LLM に渡して判定。信頼度を返す。
human
人の判定。常に最優先で、理由の記入が必須。

ジャッジの組み合わせ方と判定ポリシーの詳細は AI ネイティブ設計 を参照。

状態遷移

テストケース

stateDiagram-v2
  [*] --> draft: 作成（人 / AI）
  draft --> ready: 承認（manager 以上、AI 生成物は必須）
  ready --> draft: 大きな変更で再レビュー
  ready --> deprecated: 廃止
  deprecated --> ready: 復活

人が作った TC は作成者が manager 以上なら直接 ready にできる。draft の TC は計画に追加できるが、リリース判定の集計には含めない。

実行（run.state）と最終判定（run.verdict）

stateDiagram-v2
  [*] --> queued: 実行を開始
  queued --> running: ランナーが取得 / 人が開始
  running --> judging: 全ステップ終了
  running --> completed: 人が実行不可を選択（verdict=blocked）
  judging --> completed: 判定ポリシーで verdict 確定
  running --> error: 基盤エラー（ブラウザ起動失敗など）
  error --> [*]: 再実行は新しい RUN
  completed --> [*]
verdict表示意味次のアクション
pass合格期待結果どおり。なし
fail不合格期待結果と違う。トリアージ → Issue 作成 → 修正後に再実行
blocked実行不可前提が崩れていて実行できない（環境ダウン、データ不足、前の不具合）。原因を解消して再実行。不具合扱いにはしない。
needs_review要確認AI の信頼度不足・ビジュアル差分・P0 の人確認待ち。レビューキューで人が合格 / 不合格を確定。
skippedスキップ今回は対象外と判断した。理由必須。なし
（実行なし）未実行計画アイテムに実行がまだない。担当者が実行

人のレビューで確定した場合、元の実行の verdict を書き換えず、judge_kind = 'human' の判定を追加して再計算する。履歴は判定の列として残る。

計画アイテム（アサイン）

stateDiagram-v2
  [*] --> todo: 計画に追加・担当決定
  todo --> in_progress: 実行を開始
  in_progress --> done: 最新実行の verdict が確定（needs_review 以外）
  in_progress --> blocked: verdict = blocked
  blocked --> in_progress: 再実行
  done --> in_progress: 再テスト指示（修正デプロイ後など）

リリース

stateDiagram-v2
  [*] --> planning
  planning --> testing: 計画を開始
  testing --> ready: Go 判定（manager が承認）
  ready --> testing: 新しいデプロイで再テスト
  ready --> released: 本番リリース（GitHub release 受信または手動）

「完了」の計算

「完了したか」は人の感覚ではなく、以下のルールで計算します。計算対象は あるリリースの、ある環境（既定はプロジェクトの既定環境）です。

テストケースの「最新判定」

  1. 対象リリースに属するデプロイメントのうち、対象環境のものに対する実行を集める。
  2. その中で state = completed かつ最も新しい実行の verdict を採用する。人の判定があれば判定ポリシーで再計算した値を使う。
  3. 実行時の TC 版が現在の版より古い場合は「古い版で合格」として表示し、リリース判定では未実行扱いにする（既定）。

完了条件（AC）の状態

状態条件
未網羅ready の TC が 1 つも紐づいていない。
不合格紐づく TC のどれかの最新判定が不合格。
要確認不合格はないが、要確認がある。
未実行不合格・要確認はないが、未実行または実行不可がある。
合格紐づく TC の最新判定がすべて合格（スキップは除外。全部スキップなら未実行）。

ユースケースの状態

AC の状態を集約します。優先順は 未網羅 > 不合格 > 要確認 > 未実行 > 合格 で、AC の中で最も悪いものがユースケースの状態になります。ユースケースが「完了」とは、すべての AC が合格であることです。

網羅率

AC 網羅率 = ready の TC が 1 つ以上紐づく AC 数 ÷ AC 総数。機能・プロジェクト単位でも同じ式で集計します。

リリース判定（Go / No-Go）

リリース準備状況（S02）に表示するゲート条件です。プロジェクト設定で閾値を変更できます。全条件を満たすと「Go 可能」になり、manager が承認するとリリースが ready になります。

条件既定値設定キー
P0 ユースケースの AC 網羅率100%gate.p0_coverage
P0 テストケースの最新判定がすべて合格必須gate.p0_all_pass
P1 テストケースの合格率95% 以上gate.p1_pass_rate
P0 / P1 の要確認0 件gate.max_review
計画アイテムの未実行0 件gate.max_untested
未解決の P0 不具合（GitHub Issue）0 件gate.max_open_p0_issues
既知の問題として承認

P1 以下の不合格は、manager が理由を書いて「既知の問題」として承認すると、合格率の計算から除外できます。承認は activity_log に残り、リリース判定画面に一覧表示されます。

バージョンとスナップショット

  • TC 版は不変。手順・判定設定・フィクスチャ参照を変えると新しい版（v4）を作る。タイトル・優先度・担当者・タグは版に含めず、直接変更できる（変更は activity_log に残る）。
  • フィクスチャ版も不変。編集・アップロードのたびに新しい版を作り、R2 のパスも版ごとに分ける。「この版に戻す」は古い版の内容で新しい版を作る操作。
  • TC 版はフィクスチャを {fixture: "FX-3", version: 4}（固定）か {fixture: "FX-3", version: "latest"}（最新）で参照する。
  • 実行は開始時に全部を確定する。TC 版、フィクスチャの解決済み版（runs.fixture_versions_json）、デプロイメント、環境を記録し、後から変わらない。
  • ステップ結果には実行時点の指示と期待結果をコピーする。後で TC を直しても、過去の実行の表示は変わらない。

フィクスチャの種類

種類中身使われ方例
datasetCSV / JSON の表。1 行が 1 パターン。手順中で入力する値。行ごとに同じ TC を繰り返すデータ駆動にも使う。手順では {{FX-3.code}} のように参照。FX-3 クーポンセット、FX-9 テスト用クレジットカード
seedJSON のペイロード（対象アプリのリセット / シード API に送る）。実行前に環境を決まった状態にする。環境のリセットフック経由で送る。FX-7 ゲスト購入用の在庫
file画像・PDF などのファイル。アップロード操作のテストで使う。エージェントには一時 URL で渡す。FX-14 返品用の商品画像
accountユーザー名などの公開情報 + 秘密の参照名。ログインに使う。パスワードは Secrets Store にあり、画面ではマスク、エージェントにはツール側で注入しモデルに見せない。FX-11 staging 会員アカウント

不変条件

実装とテスト（INDX Watch 自身のユニットテスト）で守るルールです。

  • 実行は必ず 1 つの TC 版と 1 つのデプロイメントに紐づく。
  • completed の実行は verdict を持つ。needs_review は人の判定が追加されるまで計画アイテムを done にしない。
  • 人の判定（human）には理由が必須。
  • origin = 'ai' の TC・UC は、人の承認記録なしに ready にならない。
  • guest は自分が担当の計画アイテムと、その TC・環境の入り方・必要なフィクスチャ（account は自分用のみ）以外を参照できない。
  • 秘密値は D1 に保存しない。access_secret_ref / secret_ref は参照名だけ。
  • 表示キー（TC-128）は再利用しない。廃止しても番号は残る。
