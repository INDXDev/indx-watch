# Reports

A report is a rendered, self-contained snapshot that answers "is this release ready, and what is the evidence?" for people who do not use INDX Watch: customers, stakeholders, auditors. Reports are computed from the bundle plus results by the same `packages/core` functions as `iw status`.

## Contents

A release report (`iw report --release v1.2.0`) has these sections, in this order:

1. **Header** — project, release, scope (environment or "all"), generated at, generated by (actor), bundle commit (when the bundle is in a git repository), result cursor (last record included, when results came from a store).
2. **Verdict** — gate passed or not, one line per gate check with actual vs expected ([concepts](concepts.md#readiness-gate)).
3. **Summary counts** — test cases by latest status (`pass`, `fail`, `needs_review`, `stale`, `untested`, `waived`) and AC coverage, overall and by priority.
4. **Use cases** — each use case with its status and acceptance criteria; each AC with the test cases that cover it and their latest result.
5. **Failures and open items** — every `fail`, `needs_review`, `blocked`, `stale` and `untested` P0–P1 item with the run, step, note and first evidence thumbnail.
6. **Waivers** — accepted failures with reason, who, when.
7. **Coverage matrix** — use cases × ACs × test cases (rows) against latest results (cells).
8. **Run log** — every run in scope: TC, version, verdict, actor (`kind` + name), source, build, environment, time, evidence count, CI link.
9. **Appendix** — definitions of statuses and the gate thresholds used.

A plan report (`--plan PLAN-1`) replaces section 4 with plan items grouped by assignee, with due dates and computed item status.

## Formats

| Format | Use | Evidence |
|---|---|---|
| `md` | PR comments, GitHub job summaries, wikis | Links (relative to `--evidence-base`, or blob hashes) |
| `html` | Email to a customer, attach to a ticket, static hosting | Embedded as data URIs by default (`--evidence embed`), thumbnails only; size warning above 20 MB |
| `pdf` | Formal sign-off | Rendered from the HTML with a local Chromium via Playwright (`npx playwright install chromium`) |
| `json` | Machines and agents | Hashes only |

The HTML report is a single file with inline CSS, no JavaScript required, readable in light and dark mode and printable. It uses the same design tokens as the UI ([design](../design/index.html)).

## Rendering rules

- The run log shows a CI link and, for pull requests, a `PR #n` link (internal audience only).
- *(v0.2)* A run whose record claims a verified `via` without a valid signature shows "· unverified" after its actor ([signed records](security.md#signed-records)). The appendix lists `ignore_unverified` with the other gate thresholds.
- HTML reports carry a Content-Security-Policy `meta` tag; links are only rendered for `http(s)` and relative URLs; in Markdown, `&`, `<` and `>` in user-written text are escaped.
- When nothing is gated yet (the `has_gated_tests` check fails), the verdict is shown as a neutral "nothing to judge yet" state rather than a failure banner.

## Locale

`--locale en|ja` chooses UI labels and content translations (falls back to the source text, marked as such). Literal on-screen strings stay as written ([i18n.md](i18n.md#literal-strings)).

## Sharing with customers

- `--audience customer` removes: bundle `notes`, run and step notes, judgement reasons, environment guides, base URLs and access methods, actor emails (replaced by display names or "QA team"), CI URLs, and anything under `[x]`. Fixture placeholders stay unresolved (`{{FX-3.username}}`). Evidence defaults to `none` (opt in with `--evidence embed`). *(v0.2: `--include-notes` and `--include-ci-links` to keep notes and CI links.)*
- Account fixtures never appear in reports, in any audience; only their key and title.
- On the hosted app, a report can be shared via a **share link**: an unguessable token (128 bits), an expiry (default 7 days, max 90), and a fixed audience. Share links serve a frozen snapshot rendered at creation time, not live data. Creating and opening share links are recorded as records with the actor. Share-link routes are the only routes that bypass Cloudflare Access; see [Share links](#share-links) and [security.md](security.md#share-links). *(v0.2)*

### Share links

*(v0.2)* The share action lives on the web app's Report screen ([web.md](web.md#report)); the API is part of [`contract.ts`](../../packages/server/src/contract.ts).

- **Create**: `POST /api/shares` with the query of `GET /api/report` (`release`, `env`, `plan`, `audience`, `locale`, `evidence`) plus `days` (1–90, default 7). The server renders the HTML report once and stores it as a blob; the link serves those bytes, so later results never change it. The audience defaults to `customer`. Evidence defaults to `none` for customers and `embed` for internal reports; `links` is refused, because evidence links point at routes behind Access. The response (`ShareCreated`) holds the URL `<origin>/s/<token>`: the token is 128 random bits (32 hex characters) and only its SHA-256 is stored, so the URL is shown once.
- **Who**: a person signed in through Cloudflare Access (`actor.kind = "human"`, `via = "cloudflare-access"`) on the hosted app. Agents, CI service tokens, declared testers (`via = "browser"`) and the anonymous identity of a `--public` deploy get 403, and so does `iw serve`. Roles (T-301) will narrow this further.
- **Open**: `GET /s/<token>` needs no identity. It answers with the snapshot, the report CSP, `Cache-Control: no-store`, `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex`. An unknown, expired or revoked token answers 404 with nothing recorded.
- **Revoke**: `DELETE /api/shares/<id>` (the same people as create) ends a link at once. `GET /api/shares` lists every link, newest first, with its scope, audience, expiry, state (`active`, `expired`, `revoked`) and number of opens; never the token.
- **Audit**: creating, each open and revoking write one `share` record each ([sync.md](sync.md#other-records)), with the actor (opens: `{ "kind": "human", "id": "anonymous", "via": "env" }`). Links are read from these records, never only from the index, so a replica or an archive keeps the full history. A `create` or `revoke` record counts only when its actor is a person signed in through Access and, when the project pins [signing keys](security.md#signed-records), only when it is signed by one of them; others are ignored. So with pinned keys the deploy needs `IW_SIGNING_KEY` with a pinned key whose `via` allows `cloudflare-access`: without it, create and revoke answer 503 and write nothing.

## Example

For `examples/shop` with the sample results in `examples/shop/store/`, `IW_NOW=2026-11-19T00:00:00Z IW_ACTOR=qa@shop.test iw report --release v1.2.0 --format md` produces the file committed at [`examples/shop/reports/v1.2.0.md`](../../examples/shop/reports/v1.2.0.md). The bundle commit line is omitted when `IW_NOW` is set. CI regenerates it and fails on any difference.

## Acceptance criteria

- [x] `iw report --format html` works offline and produces one file with no external requests (checked by loading it in Playwright with network disabled).
- [x] `--audience customer` output contains no email addresses and no `notes` text from the bundle (tested on `examples/shop`).
- [x] The Markdown report for `examples/shop`, generated with the fixed `IW_NOW` and `IW_ACTOR`, matches the committed example byte-for-byte.
- [x] The gate section of the report equals the `gate` object of `iw status --json` for the same scope.
- [x] A share link serves its frozen snapshot without an identity, unchanged by later results; after its expiry or revocation it answers 404 (server and Worker tests).
- [x] Creating, opening and revoking a share link each write a `share` record with the actor; only a person signed in through Cloudflare Access on the hosted app can create or revoke one (server test). With pinned signing keys, `create` and `revoke` records written straight to the bucket (unsigned, or with a self-asserted `via`) never count, and creating answers 503 when the server cannot sign (Worker test).
