ポータビリティとローカル同期（Watch Bundle と iw CLI）

テストの仕様・データ・結果を、決められたディレクトリ構成と型を持つファイル群（Watch Bundle）として定義します。Cloudflare 上の INDX Watch は、その形式のデータを見て・管理して・共有するための場所の 1 つです。indx-watch/ フォルダに設定ファイルを 1 つ置けば、インストールなしのコマンド 1 つで手元に丸ごと取り出せ、編集して戻せます。同じフォルダから Cloudflare への構築・デプロイも 1 コマンドで行えます。

状態 ドラフト v0.1更新 2026-11-19関連 データモデル · アーキテクチャ · S13 データの持ち出し

なぜ必要か

  • ロックインしない: 仕様やテスト結果は会社の資産です。Cloudflare をやめても、INDX Watch 自体をやめても、データが標準的なファイルとしてそのまま残るようにします。
  • Git の良さ: 手元のファイルなので、エディタで編集でき、差分が見え、grep でき、Claude Code などの AI がそのまま読み書きできます。
  • Google ドライブの良さ: 同期は 1 コマンド（常時同期も可）。Git のように commit・push・merge を意識しなくてよく、ビジネス職や顧客はブラウザだけで使えます。
  • 自由すぎない: 何でも置けるフォルダにすると管理が崩れます。ディレクトリ構成・ファイル名・項目を INDX Watch が決め、型で検証します。テンプレートもこちらで用意します。

原則: 形式が正、置き場所は入れ替えられる

「単一の情報源」は特定のデータベースではなく、Watch Bundle という形式と、その中身です。D1 も手元のフォルダも、その形式のデータを置く場所です。

置き場所役割持っているもの
Watch Bundle 形式（packages/bundle）データの形の定義。型（スキーマ）、ディレクトリ構成、正規化のルール—
クラウド（Cloudflare の D1 + R2）共有と同期の中心。画面・AI 実行・権限・ログ全部（すべての版・実行・証拠・ログ）
作業コピー（indx-watch/）手元で読む・編集する・オフラインで使う今の版の仕様・データ・計画と、最近の実行結果。証拠は必要なときだけ
フル書き出し（アーカイブ 1 ファイル）バックアップ・移行・監査。別の INDX Watch にそのまま取り込める全部（ログは admin が指定したときだけ）

サーバーと CLI は同じ packages/bundle を使い、同じ正規化（項目の順序・改行・ハッシュ）をします。そのため「サーバーの内容」と「手元のファイル」が同じかどうかを、ハッシュの比較だけで判断できます。

3 つの使い方

1. 同期（作業コピー）

iw clone で取り出し、iw pull / iw push（または iw sync --live）で同期。普段使い。

2. フル書き出し・取り込み

iw export --full でアーカイブ 1 ファイルに。iw import で別のインスタンスへ。バックアップと移行。

3. ローカル専用

watch.toml の server を空にすると、サーバーなしでファイルだけで使える。検証・完了計算・手動実行の記録まで手元でできる。

ディレクトリ構成

どのリポジトリにも（リポジトリでなくても）置けます。フォルダ名は indx-watch/ に固定します。

ファイル形式

構造は TOML、データの本体は CSV / JSON / 画像などそのままの形式です。TOML を選んだ理由は、人が読み書きしやすく、複数行の文字列が書け、コメントが書け、型がはっきりしているためです。CLI はファイルを書くときに必ず正規化（キーの順序、改行、引用符）するので、差分がきれいに出ます。

watch.toml

#:schema https://dl.watch.indx.example/schemas/v1/watch.json

schema_version = 1
server = "https://watch.indx.example"   # 空ならローカル専用モード
project = "SHOP"

[sync]
include = ["specs", "fixtures", "environments", "releases", "plans", "runs"]
runs_since = "90d"          # 何日分の実行結果を持ってくるか
evidence = "on-demand"      # none | on-demand | all
commit = []                 # Git に含めたいもの（例: ["specs", "fixtures/*.toml"]）。既定は設定と起動スクリプトだけ
live_interval = "10s"       # iw sync --live の間隔

[cli]
version = "1.0.0"           # 起動スクリプトが取得する CLI の版（固定）

ID とファイル名

  • ファイルの同一性は中の id（{prefix}_{ULID}）で判断します。ULID は手元でも作れて衝突しないので、オフラインで新しいテストケースを作っても問題ありません。
  • 新規作成: iw new tc --uc UC-12 --template checkout で、id 付き・key なしのファイル（TC-new-….toml）ができます。push するとサーバーが番号（TC-131）を振り、CLI がファイル名と key を書き換えます。
  • ローカル専用モードでは、番号は .watch/counters.json で手元で振ります。後でサーバーに取り込むとき、番号が空いていればそのまま、使われていれば振り直して対応表をレポートに出します。
  • 表示キー（TC-128）や AC のキー（AC-12.2）での参照（covers、fixtures、test_case）は、取り込み時に id に解決します。

型（スキーマ）

  • 正は zod: packages/bundle/src/schema/v1/*.ts に zod で定義し、そこから JSON Schema（schemas/v1/*.json）を生成します。サーバー、CLI、エディタが同じ型を使います。
  • エディタ補完: 各ファイルの先頭の #:schema 行で、TOML 対応のエディタ拡張が補完と検証をします。スキーマは CLI と同じ配布先に置きます（配布）。
  • 版: schema_version は整数です。項目の追加など後方互換の変更では上げません。名前の変更・削除など互換性のない変更で上げ、iw migrate で手元のファイルを書き換えます。サーバーは 1 つ前の版も受け付けます。
  • データモデルとの関係: Bundle の型は D1 のテーブルを人が扱いやすい形にまとめたものです（対応表）。テーブルを変えるときは Bundle の型と対応表も同じ PR で更新します。

同期の仕組み

sequenceDiagram
  autonumber
  participant L as iw CLI（手元）
  participant W as web Worker /api/sync/v1
  participant D as D1
  L->>W: GET changes?since=rev（Access を通過）
  W->>D: sync_changes から rev より後の変更
  W-->>L: 変更された実体（正規化した Bundle 表現 + content_hash）と新しい rev
  L->>L: 手元が未変更なら上書き。変更ありなら 3 方向マージ（base / 手元 / サーバー）
  L->>W: POST push（実体ごとに base_hash と新しい内容）
  W->>W: 現在の正規化ハッシュ == base_hash か確認
  alt 一致
    W->>D: 画面からの更新と同じ処理（withAudit, via=cli）。手順の変更は新しい版
    W->>D: sync_changes に rev を追加
    W-->>L: 新しい hash・rev・（新規なら）採番した key
  else 不一致（誰かが先に変えた）
    W-->>L: 409 と現在の内容
    L->>L: 3 方向マージ。同じ項目の衝突は X.remote.toml を作り、push を止める
  end
  • 変更の検出: .watch/state.json に、ファイルごとの id・前回同期時のハッシュ・rev を持ちます。.watch/base/ に前回同期時の内容を保存し、3 方向マージの基準にします。
  • マージの単位は項目: サーバーと手元で違う項目（例: サーバーで翻訳、手元で手順）を変えていれば自動でまとめます。同じ項目を両方で変えたときだけ衝突にし、X.remote.toml を作って iw status に表示します。解決したら iw resolve X。
  • 版は守られる: テストケースの手順やフィクスチャの本体を変えて push すると、サーバーで新しい版が作られます。手元のファイルは常に今の版です。
  • 削除: ファイルを消して push するとアーカイブ（論理削除）になります。確認のため --allow-archive が必要です。
  • 読み取り専用の項目: version、実行結果、承認者、サーバーが計算する値は、手元で変えても push で拒否します（iw check が事前に警告）。
  • 権限は画面と同じ: guest が clone すると、自分にアサインされた範囲だけが取れます。draft → ready などの承認は manager 以上でないと拒否されます。
  • 大きなファイル: フィクスチャ本体と証拠は R2 の presigned URL で直接やり取りし、内容のハッシュで重複を避けます。
  • 常時同期（--live）: 手元のファイル変更を監視して数秒後に push、live_interval ごとに pull します。Google ドライブのデスクトップアプリと同じ使い心地を目指します。

Git との付き合い方

  • 既定は「設定だけコミット」: 自動生成する .gitignore は、watch.toml・iw・iw.cmd・.gitignore 以外をすべて無視します。リポジトリを clone した人は ./iw clone だけで中身がそろいます。同期はサーバーが担うので、Git の衝突は起きません。
  • 仕様も Git に入れたい場合: [sync] commit = ["specs"] にすると .gitignore が書き換わり、specs/ がコミット対象になります。PR で仕様の差分をレビューしたいチーム向けです。この場合も正はサーバーで、iw sync で揃えます。
  • CI での利用: 対象リポジトリの CI で ./iw check（オフライン）や ./iw report --release … を実行できます。

CLI の認証と ID

CLI のコード自体は公開してかまいません。守るべきなのはデータに入るための認証情報で、これは Cloudflare 公式のツールが発行するものをそのまま使います。iw は公式 CLI を呼ぶ薄い包み（ラッパー）で、独自の認証の仕組みは作りません。共有の鍵も、ログが残らない Bypass も使いません。

用途包む公式ツールやることアプリ・Cloudflare での記録
データの読み書き（clone / sync / export など）cloudflared accessiw login = cloudflared access login https://watch.indx.example（ブラウザで Google Workspace / OTP）。以降のリクエストごとに cloudflared access token -app=… で取ったトークンを cf-access-token ヘッダで送る本人の ID に結びついたトークン。Access のログイン記録に残り、アプリには本人として届く。login_sessions.client = 'iw:cloudflared'、activity_log.via = 'cli'
デプロイ（iw deploy / iw dev）wranglerwrangler login（OAuth）か環境変数 CLOUDFLARE_API_TOKEN をそのまま使う。リソース作成・デプロイ・マイグレーションは wrangler のコマンドを順に呼ぶCloudflare の監査ログ（Audit Logs v2）に本人として残る
無人実行（CI・MCP）Access のサービストークンCF-Access-Client-Id / CF-Access-Client-Secret を環境変数から送る（strict 設定・タグ付き）auth_kind = 'service_token'。トークンごとに担当の agent ユーザーと発行者を記録
  • インストール不要のまま: cloudflared が入っていなければ、iw が公式の配布元（GitHub Releases）から OS に合った単一バイナリを取得し、チェックサムを確かめて ~/.cache/indx-watch/ に置きます。wrangler は npx で呼びます。
  • トークンの置き場所: cloudflared 自身の保存場所（~/.cloudflared/）に任せ、iw は保存しません。期限（Access アプリのセッション時間）が切れたら iw が自動で cloudflared access login をやり直します。
  • 公式の位置づけ: cloudflared access token は「利用者本人が、コマンドラインから API を使うためのもの」として案内されています（無人のサービス向けではない）。iw の使い方はこれに一致します。
  • 次の候補: Access の Managed OAuth（2026-03〜 open beta）が正式になったら、cloudflared なしで同じことができるようにします（login_sessions.client = 'iw:oauth'）。設計は変わりません。
  • アプリ側の API: Access が Authorization ヘッダを使う場合があるため、INDX Watch の API は独自の Authorization を使いません。
M2 の最初に PoC で確かめること
  • cf-access-token で入ったリクエストが、オリジンに Cf-Access-Jwt-Assertion（本人の sub・email・identity_nonce）付きで届くこと。
  • そのトークンを CF_Authorization Cookie として渡して get-identity が使えるか。使えない場合、IdP は Access のログ（access_events.connection）から補う。
  • One-time PIN + Independent MFA の顧客でも cloudflared access login が通るか。通らない場合、顧客は CLI を使わずブラウザのみとする。

インストール不要の配布

「入れる」作業をなくすため、Gradle の gradlew と同じ考え方で、indx-watch/ に小さな起動スクリプト iw（Windows は iw.cmd）を置きます。起動スクリプトは watch.toml の [cli] version を読み、その版の CLI を呼びます。チーム全員が同じ版を使えます。

  1. Node.js 20 以上がある場合（既定）: npx -y @indx/watch@1.0.0 … を実行します。npm のキャッシュに入るので 2 回目からはすぐに起動します。パッケージは npm の公開パッケージ @indx/watch です（R2 に置いた tarball の URL からも取得できます）。
  2. Node がない場合: R2 から単一バイナリ（Bun でビルド。macOS arm64 / x64、Linux x64 / arm64、Windows x64）を取得し、sha256 を確かめてから ~/.cache/indx-watch/1.0.0/ に置いて実行します。
置くもの場所理由
単一バイナリ（拡張子 .tar.gz / .zip）とチェックサムR2 + Access の外のカスタムドメイン dl.watch.indx.exampleWorkers の静的ファイルは 1 ファイル 25 MiB までで足りない。r2.dev は本番向けでない。拡張子付きならキャッシュされる
init.sh / init.ps1同上indx-watch/ に watch.toml と起動スクリプトを置くだけの小さなスクリプト
JSON Schema（schemas/v1/*.json）同上（JSON Schema Store にも登録）エディタの補完用。Access の外に置かないとエディタから読めない
  • 公開してよい（2026-11-19 決定）: CLI のコードと配布物に秘密は含まれず、データに入るには iw login（Cloudflare Access の本人確認）が必要です。npm は公開パッケージ（@indx/watch）でかまいません。
  • エディタ: 各ファイルの先頭の #:schema 行（直後に空行を 1 行）で、Tombi（推奨）か Even Better TOML が補完と検証をします。

フォルダから 1 コマンドでデプロイ

indx-watch/ には「データ」と「どこに置くかの設定」がそろっています。そのため、このフォルダ 1 つから、Cloudflare 上に INDX Watch 一式を作ってデータを入れるところまでを iw deploy 1 回で行えます。別のアカウントへの引っ越しや、チームごとの専用インスタンスも同じ手順です。

watch.toml の [deploy]

[deploy]
target = "cloudflare"
account_id = "0123abcd…"            # 秘密ではない。API トークンは環境変数か wrangler のログインで渡す
name = "indx-watch"                 # リソース名の接頭辞（indx-watch-web, indx-watch-files …）
domain = "watch.indx.example"
version = "1.0.0"                   # デプロイするアプリの版（CLI と同じ版）

[deploy.access]
team = "indx"                       # Zero Trust のチーム名
employee_domains = ["indx.example"] # Google Workspace のドメイン
guests = ["yamamoto@sample.example"]  # 顧客（One-time PIN + MFA）
session = { employee = "12h", guest = "8h" }

[deploy.ai]
gateway = "indx-watch"              # Anthropic のキーは AI Gateway の BYOK に登録しておく

iw deploy がすること

  1. 計画の表示: 作る・変えるリソースの一覧を出して確認を求める（--dry-run は表示だけ）。
  2. リソースの用意: D1、R2（ファイル用・バックアップ用、ライフサイクル付き）、Queues、Workflows を、名前で探して無ければ作る（何度実行しても同じ結果になる）。作った ID は .watch/deploy.json に記録。
  3. アプリの配置: CLI に同梱した web / runner のビルド済み成果物と wrangler 設定のひな形から設定を生成し、runner → web の順にデプロイ。
  4. DB の準備: D1 のマイグレーションを適用。
  5. 入口の保護: Access アプリを Worker に付け、[deploy.access] のポリシーを作る（社員ドメイン、顧客の個別メール + Independent MFA、セッション時間）。Webhook パスの Bypass も作る。
  6. データの投入: フォルダの中身（作業コピー、またはフル書き出しのアーカイブ）を取り込む。
  7. 確認: ヘルスチェックを行い、URL と、人が残りで行うこと（IdP の接続、Logpush、BYOK キーの登録など未設定の項目）を表示する。
  • Cloudflare の認証情報: iw deploy は wrangler を呼ぶだけなので、wrangler login の OAuth か CLOUDFLARE_API_TOKEN をそのまま使う。Access アプリとポリシーの作成は Cloudflare API を呼ぶため、Access の編集権限を持つ CLOUDFLARE_API_TOKEN があるときだけ自動で行い、なければ手順を表示する。watch.toml には書かない。
  • 更新: [deploy] version を上げて iw deploy すると、マイグレーション → runner → web の順に更新する。
  • 手元で同じアプリ: iw dev は同じ成果物を wrangler のローカル環境（D1・R2 の模擬）で起動し、フォルダの中身を取り込んで http://localhost で開きます。画面での変更はフォルダに書き戻されます（手元のサーバーと同期する）。iw serve（読み取り専用の閲覧）より機能が多い「手元の INDX Watch」です。
  • INDX Watch 自身の開発: このリポジトリの GitHub Actions は従来どおりソースからデプロイします。iw deploy はリリース済みの版を、利用するチームが自分のアカウントに立てるための手段です。

ローカルでのテスト管理

  • 検証と計算: iw check と iw report は、サーバーと同じ packages/core（完了計算・Go / No-Go）を CLI に同梱して動かします。結果はサーバーの S02 と一致します。
  • 手動実行の記録: iw run は手順を 1 つずつ表示し、合否・メモ・スクリーンショットのパスを受け取って runs/local/ に記録します。push するとサーバーの実行になり、executor は CLI でログインした本人、via = 'cli'、オフラインで記録したことと手元の時刻が残ります。
  • 閲覧: iw serve は手元のファイルだけを読む閲覧画面（仕様ツリー、準備状況、実行結果）を localhost で開きます。ローカル専用モードの「見る場所」になります。
  • AI で編集: 作業コピーは Claude Code などがそのまま読み書きできます。AI が作ったファイルには origin = "ai" を付けるよう求め、push 時にサーバーで draft として扱います（原則 5）。

フル書き出し・取り込み

作業コピーは「今の状態」だけですが、フル書き出しは失うものがない完全なコピーです。別の INDX Watch（別アカウントの Cloudflare、将来の別基盤、ローカル専用）にそのまま取り込めます。

indx-watch-export-SHOP-20261119T100000Z.tar.zst
├── manifest.json        # schema_version, 書き出し元, 日時, 件数, 全ファイルの sha256
├── working/             # 作業コピーと同じ構成（今の状態）
├── history/             # すべての版と記録（1 行 1 レコードの NDJSON）
│   ├── test_case_versions.ndjson
│   ├── fixture_versions.ndjson
│   ├── runs.ndjson  run_steps.ndjson  judgements.ndjson  evidence.ndjson
│   ├── translations.ndjson  ai_suggestions.ndjson  comments.ndjson  baselines.ndjson
│   ├── deployments.ndjson  issues.ndjson  sync_changes.ndjson
│   └── audit/           # --include-audit のときだけ（admin）
│       ├── activity_log.ndjson  login_sessions.ndjson  access_events.ndjson  page_views.ndjson
└── blobs/sha256/ab/cd…  # 証拠・フィクスチャ本体・ベースライン（内容ハッシュで 1 つずつ）
  • 書き出し: サーバーの Workflow がアーカイブを作って R2 に置き、署名付き URL で渡します（7 日で削除）。S13 または iw export --full から実行。
  • 取り込み: まず --dry-run で差分レポート（追加・更新・衝突・番号の振り直し）を出し、確認してから適用します。ID（ULID）はそのまま保ちます。
  • 定期バックアップ: 毎週、全プロジェクトのフル書き出しをバックアップ用バケットに置きます（D1 のエクスポートとは別に、形式で残す）。
  • 個人に関するデータ: ログイン・行動ログは --include-audit（admin のみ）を付けたときだけ含めます。書き出したこと自体が activity_log に残ります。

守ること

  • 秘密は Bundle に入れない: 環境の認証情報・テストアカウントのパスワードは参照名だけ。iw check は秘密らしい値（トークンの形、password = など）を見つけたら push を止めます。
  • 形式を勝手に広げない: 新しい項目は zod の型に足してから使う。知らない項目を含むファイルは push で拒否する。
  • 正規化を通す: CLI もサーバーも、ファイルを書くときは必ず packages/bundle の書き出し関数を使う（手書きのフォーマットを作らない）。
  • 互換性: schema_version を上げる変更は、移行関数とテストを同じ PR に入れる。

完了条件

  • SHOP のサンプルを iw clone して、何も変えずに iw push しても差分が 0（正規化が往復で一致する）。
  • フル書き出し → 空のインスタンスに取り込み → もう一度フル書き出しすると、manifest.json の件数と全ハッシュが一致する（ログを含む場合も）。
  • 手元で手順を変えて push すると新しい版ができ、画面に反映され、activity_log に本人・via = 'cli' が残る。
  • サーバーと手元で別の項目を変えると自動でまとまり、同じ項目だと衝突になって push が止まる。
  • ローカル専用モードで、iw check・iw report・iw run・iw serve がサーバーなしで動く。
  • macOS / Linux / Windows で、追加のインストールなしに ./iw clone が動く（Node があれば npx、なければ単一バイナリ。初回の取得を含めて 30 秒以内）。
  • iw login（cloudflared access）後の CLI からの書き込みが、ブラウザと同じ本人の ID で activity_log に残る。
  • 空の Cloudflare アカウントに対して、indx-watch/ から iw deploy 1 回で INDX Watch が立ち上がり、フォルダのデータが画面に出る（IdP 接続など人の作業は一覧で表示される）。
