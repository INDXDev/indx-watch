SPEC-05 · アーキテクチャ

Cloudflare 上の構成

INDX Watch は Worker 2 つ（UI + API の indx-watch-web、実行基盤の indx-watch-runner）と、D1・R2・Browser Run（旧 Browser Rendering）・Workflows・Queues・Email Routing・Access で構成します。自前のサーバー・コンテナは持ちません。Cloudflare の仕様は頻繁に変わるため、前提にした仕様と出典を 最新仕様の確認メモ にまとめています。

状態 ドラフト v0.2更新 2026-11-19関連 認証・行動ログ · データモデル · AI ネイティブ設計 · 実装ガイド

全体構成

利用者のブラウザからのアクセスはすべて Cloudflare Access を通ります。例外は GitHub からの Webhook（署名で検証）だけです。テストの実行は web から runner にジョブを渡し、runner が Browser Run 上のブラウザで対象環境を操作します。対象アプリが送るメール（注文確認など）は Email Routing で受け取り、runner の Email ハンドラーが実行に結び付けます。

並列度

Browser Run の上限は同時 200 ブラウザ・新規起動 毎秒 3 ですが、料金は「日次ピーク同時数の月平均」が 10 を超えると 1 つあたり $2 かかります。max_concurrency を 4（既定）にして、月平均 10 以内に収めます。web 側の手動実行（スクリーンショット添付のみ）はブラウザを使わないので、この上限の対象外です。

認証・認可

ログイン履歴・失敗したログイン・セッション・画面ごとの行動ログを「いつ・どこで・どう」まで記録する設計は SPEC-09 認証・行動ログ にあります。ここでは Access の構成とリクエストの検証だけを扱います。

Cloudflare Access の設定

2026-08 から Access のポリシーを Worker そのものに付けられるようになりました。これを使うと、カスタムドメインだけでなく workers.dev や Preview URL も同じポリシーで保護されます。新規アカウントの既定 IdP は Cloudflare IdP（2026-06〜）で、社内メンバーは社内の IdP、顧客はワンタイム PIN（メールごとに手動で許可）でログインします。

M1 で実機確認すること

Worker 単位の Access 保護と、パス単位の Bypass アプリが重なったときにどちらが優先されるかは、ドキュメントで確認できていません。M1 の最初に staging で確かめ、Bypass が効かない場合は Webhook 受信を別の小さな Worker（Access なし、HMAC 検証のみ、Queue に積むだけ）に分けます。

顧客を招待するときは、manager が S09 から招待し、その場でメールアドレスを Access ポリシー（Access の API を使用）と users（role = guest）に追加します。招待を外すと両方から削除し、Access のセッションも失効させます。

  W-->>B: 画面（guest は自分のアサイン分だけ）

JWT 検証のルール

  • jose で検証する: createRemoteJWKSet で https://<team>.cloudflareaccess.com/cdn-cgi/access/certs を取得し、jwtVerify でヘッダーの kid に合う鍵を選び、署名・aud（POLICY_AUD）・iss（TEAM_DOMAIN）・exp を確認します。鍵セットは Worker のメモリにキャッシュします。署名鍵は約 6 週ごとにローテーションされ、古い鍵は 7 日間有効です。
  • ctx.access は使わない: 2026-08 に追加された公式ヘルパー ctx.access は、Static Assets を持つ Worker には渡されません。vinext（Vite プラグインが assets を追加する）でも OpenNext でも該当しうるため、jose による検証を正とします。
  • ヘッダーだけを信用しない: 検証はヘッダー Cf-Access-Jwt-Assertion で行います。CF_Authorization クッキーは届く保証がありません。Cf-Access-Authenticated-User-Email ヘッダーは検証なしで信用しません。
  • JWT にあるもの: aud, email, exp, iat, nbf, iss, type, identity_nonce, sub, country。カスタムクレームは認可に使いません。IdP の種類・グループ・デバイス情報は JWT に含まれないため、セッションの最初に /cdn-cgi/access/get-identity を 1 回呼んで取得します（詳細は SPEC-09）。
  • ローカル開発では DEV_USER_EMAIL を設定したときだけ検証をスキップします（本番ビルドでは無効）。
  • 社内ドメイン以外のメールで users に存在しない場合は 403 にします（自動作成しない）。

対象環境へのアクセス

テスト対象の環境（environments）ごとに「どうやって入るか」を access_kind で持ちます。runner はブラウザを起動するときに、ここから認証情報を組み立ててブラウザコンテキストに設定します。秘密値はモデルにも画面にも出しません。

access_kind例runner の処理人がテストするとき
none公開ステージング何もしないURL を開くだけ
cf_accessstaging https://staging.shop.example.comSecrets Store の access_secret_ref から Client ID / Secret を取り出し、CF-Access-Client-Id / CF-Access-Client-Secret を対象オリジンへのリクエストにだけ付ける。setExtraHTTPHeaders は全リクエスト（外部の決済画面や CDN も含む）に付くので使わない。page.route でホストを判定して付けるか、Browser Run の outboundByHost（対象ホスト宛ての通信を runner 内の関数経由にし、そこでヘッダーを足す）を使う社内アカウントで Access ログイン（S09 に手順を表示）

  • テストアカウント（fixture kind = account）のパスワードも Secrets Store に置き、fixture_versions.secret_ref に参照名だけを保存します。
  • エージェントが入力するときは、モデルには {{FX-11.password}} というプレースホルダだけを見せ、fill ツールの実行時に runner が置き換えます（AI ネイティブ設計）。
  • 証拠のスクリーンショットでは、type=password の入力欄とフィクスチャで「マスク」指定した要素を塗りつぶしてから保存します。
  • Bot 判定に注意: Browser Run の通信は常に bot として扱われます。対象環境のゾーンで Bot Fight Mode が有効だとブロックされることがあります。WAF のスキップルールで Browser Run だけ通すには Enterprise プランが必要なので、テスト環境では Bot Fight Mode を切るか、Access サービストークンで入る構成にします（テスト対象の登録）。

  • Workflow のステップは冪等にします（同じ run_id と seq で上書き）。
  • キャンセルは web から service binding 経由で Workflow インスタンスを terminate し、runs.state = error、verdict = skipped にします。
  • 計画の一括実行（例: PLAN-4 の agent 対象 31 件）は 1 件ずつ Queue に入れ、max_concurrency で同時ブラウザ数を抑えます。
  • Browser Run は無操作 60 秒でセッションを閉じます。人の確認待ちの間はブラウザを閉じ（waitForEvent 中にブラウザは持たない）、必要なら新しいセッションで続きから再開します。keep_alive は最大 20 分なので、ログイン引き継ぎ（下記）でのみ使います。
  • Browser Run は新バージョンのリリース時に既存セッションを閉じることがあります。browse ステップは「ブラウザが閉じられた」エラーを基盤エラーとして扱い、1 回だけ最初のステップからやり直します。
  • 定期実行: D1 の schedules が正です。schedule-dispatch Workflow を 5 分ごとに起動し（Workflow の schedules、UTC）、期限の来た行を Queue に入れます。行ごとに Cron Trigger を作らないので、画面から設定を変えてもデプロイは不要です。

監査・バックアップ・保持

  • 監査ログ: 仕様・計画・フィクスチャ・判定・権限の変更はすべて activity_log に差分付きで記録。ログイン情報の閲覧（S09）も記録します。
  • バックアップ: D1 Time Travel（30 日以内の任意時点に戻せる）に加え、毎日 JST 3:00 に D1 のエクスポートを R2 の別バケット indx-watch-backup に保存（90 日保持）。エクスポート中は D1 への他のリクエストがブロックされるため、利用の少ない深夜に行います。FTS5 の仮想テーブル（search_index）を含むダンプは D1 に再インポートできないので、復元時は仮想テーブルを除いて取り込み、索引は再構築します。
  • データ保持: 証拠ファイル（evidence/、録画・trace を含む）は R2 ライフサイクルで 30 日後に低頻度アクセス層へ移し、180 日後に削除。D1 の evidence 行は残し「期限切れ」と表示。リリースの最終結果に使われた証拠は retain フラグで保持期間外にできます。フィクスチャとベースラインは削除しません。
  • 可観測性: Workers Observability（ログ・トレース）と AI Gateway のログを使い、独自の監視基盤は作りません。利用者の行動ログは D1 に持ちます（SPEC-09）。
  • AI Gateway のログ: cf-aig-metadata（最大 5 件）に project_key・run_id・feature・user_id を付けます。テストアカウントの値や対象画面の個人情報を含みうる呼び出し（エージェント・ジャッジ）は cf-aig-collect-log-payload: false で本文を保存させず、トークン数とコストだけを残します。
  • R2 のイベント通知: evidence/ への object-create を Queue に送り、サムネイル生成とビジュアル差分を非同期に行います。

主要な設計判断

ADR-001

Next.js を vinext で Workers に載せる（v0.2 で変更）

決定: UI と API を 1 つの Next.js（App Router）にまとめ、Cloudflare が推奨する vinext（Vite ベース、1.0）で Worker にする。M1 の初週に npx vinext check を CI に入れる。"use cache"（Cache Components）は vinext の対応が限定的なので使わない。

理由: Server Components と Server Actions で API 層を別に書かずに済み、コード量が最も少ない。新規アプリなので互換性の差の影響を受けにくい。Worker のサイズ上限が 64 MiB（非圧縮）になり、バンドルサイズの心配もほぼない。

フォールバック: 互換性で問題が出たら @opennextjs/cloudflare 1.20.x（Next 15.5.29 以上 / 16.4.5 以上、Node runtime）に切り替える。アプリのコードは Next.js の API だけを使い、アダプター固有の API に依存しない。

ADR-002

実行は Cloudflare Workflows

決定: 1 実行 = 1 Workflow インスタンスとし、準備・操作・ジャッジ・確定をステップに分ける。

理由: 数分かかる処理を途中から再開でき、ステップ単位のリトライとタイムアウトが標準で付く。waitForEvent で人の判定やメールの到着を最大 365 日まで待てる。schedules で定期起動もできる。状態管理を自前で書かなくてよい。

代わりに諦めること: ステップ間で渡せるデータは小さくする（大きなものは R2 に置いてキーだけ渡す）。

ADR-003

v1 では Durable Objects を必須にしない

決定: 実行中の進捗はポーリング（2 秒間隔、実行中の画面のみ）で表示する。Durable Objects（SQLite、Free プランでも利用可）は禁止はしないが、v1 の必須部品にはしない。

理由: リアルタイム共同編集やロックの要件が v1 にはない。状態の置き場所が D1 と二重になるのを避ける。

見直す条件: ブラウザセッションの再利用、Sandbox SDK の導入、実行ビューアのライブ配信が必要になったとき。

ADR-004

D1 を唯一の正にする

決定: 仕様・計画・結果は D1 が正。リポジトリへの YAML 書き出しは M3 以降に「エクスポート」として提供し、取り込みは AI 仕様取り込み経由とする。

理由: ビジネス職がブラウザで編集でき、実行結果と同じ DB で結合できる。リポジトリと DB の双方向同期は衝突処理のコストが大きい。

ADR-005

エージェントは Playwright の自前ツールで操作する

決定: Claude の computer use ではなく、a11y ツリーの ref を使う自前ツール（navigate / click / fill など）で操作する。

理由: DOM を直接扱えるので座標推定より安定し、トークンが少なく安い。操作ログがそのまま Playwright スクリプトに変換できる。

例外: canvas 中心の UI だけ computer_toolset_20260801 を検討する。Browser Run の Stagehand 対応や実験的エンジン Kitesurf は、操作の再現性を優先して使わない。

ADR-006

LLM 呼び出しは AI Gateway 経由（BYOK）

決定: Anthropic SDK の baseURL を AI Gateway の Anthropic エンドポイントに向ける。Anthropic のキーは Gateway の BYOK（Secrets Store）に置き、byok_only を有効にする。spend limits を設定する。

理由: 呼び出しログ・コスト集計・レート制限・上限停止を自前で作らずに済む。Worker がキーを持たないので漏えい面が減る。

翻訳: 日英翻訳も Claude を使う。Workers AI の m2m100-1.2b は日本語対応がドキュメントで確認できないため採用しない（安価な代替として品質検証の候補にとどめる）。

ADR-007

Containers / Sandbox は v2 の候補

決定: v1 は Browser Run + @cloudflare/playwright だけで実行する。

理由: Browser Run は Playwright Test ランナーと動画録画に対応しないが、v1 の要件（ステップ実行・スクリーンショット・trace・セッション録画）は満たせる。

見直す条件: 既存の @playwright/test スイートをそのまま回したい、動画が必要、Firefox / WebKit が必要になったとき。Containers / Sandbox SDK（GA）で実行する。

ADR-008

テスト用メールは Email Routing で受ける

決定: テスト専用の apex ドメインの catch-all を runner の email() に向け、実行ごとのアドレスで待ち合わせる。

理由: 外部のメールボックスサービスや人の目視なしに、メールを含む完了条件を自動で検証できる。追加費用がかからない。
