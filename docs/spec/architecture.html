SPEC-05 · アーキテクチャ

Cloudflare 上の構成

INDX Watch は Worker 2 つ（UI + API の indx-watch-web、実行基盤の indx-watch-runner）と、D1・R2・Browser Rendering・Workflows・Queues・Access で構成します。自前のサーバー・コンテナは持ちません。

状態 ドラフト v0.1更新 2026-11-19関連 データモデル · AI ネイティブ設計 · 実装ガイド

全体構成

利用者のブラウザからのアクセスはすべて Cloudflare Access を通ります。例外は GitHub からの Webhook（署名で検証）だけです。テストの実行は web から runner にジョブを渡し、runner が Browser Rendering 上のブラウザで対象環境を操作します。

並列度

max_concurrency は Browser Rendering の同時ブラウザ数の上限（契約プランで決まる）より小さくします。web 側の手動実行（スクリーンショット添付のみ）はブラウザを使わないので、この上限の対象外です。

認証・認可

Cloudflare Access の設定

Access アプリパスポリシーWorker 側の検証
INDX Watch（メイン）watch.indx.example/*Allow: メールドメインが社内ドメイン（IdP: Google Workspace）
Allow: 招待済み顧客のメールアドレス（ワンタイム PIN）
セッション 24 時間		Cf-Access-Jwt-Assertion を検証し、users と突き合わせる
GitHub Webhookwatch.indx.example/api/github/webhookBypass（誰でも到達可）X-Hub-Signature-256 を GITHUB_WEBHOOK_SECRET で HMAC 検証。失敗は 401
MCPwatch.indx.example/mcpService Auth: 発行したサービストークンのみJWT の common_name（サービストークン ID）を users（kind = agent）に対応付け、その所有者の権限で動かす

顧客を招待するときは、manager が S09 から招待し、その場でメールアドレスを Access ポリシー（Access の API を使用）と users（role = guest）に追加します。招待を外すと両方から削除します。

リクエストごとの流れ

sequenceDiagram
  participant B as ブラウザ
  participant A as Cloudflare Access
  participant W as indx-watch-web
  participant D as D1
  B->>A: GET /p/SHOP/releases/v2.4.0
  A->>A: IdP または OTP でログイン済みか確認
  A->>W: リクエスト + Cf-Access-Jwt-Assertion
  W->>W: JWT 検証（チーム証明書 certs で署名、aud = CF_ACCESS_AUD、exp）
  W->>D: users を email で検索（なければ社内ドメインのみ tester で作成）
  D-->>W: user（role）+ project_members
  W->>W: 権限チェック（core/authz）
  W-->>B: 画面（guest は自分のアサイン分だけ）
  • JWT 検証は jose の createRemoteJWKSet で https://{CF_ACCESS_TEAM_DOMAIN}/cdn-cgi/access/certs を取得し、jwtVerify で issuer と audience を確認します。鍵セットは Worker のメモリにキャッシュします。
  • ローカル開発では DEV_USER_EMAIL を設定したときだけ検証をスキップします（本番ビルドでは無効）。
  • 社内ドメイン以外のメールで users に存在しない場合は 403 にします（自動作成しない）。

対象環境へのアクセス

テスト対象の環境（environments）ごとに「どうやって入るか」を access_kind で持ちます。runner はブラウザを起動するときに、ここから認証情報を組み立ててブラウザコンテキストに設定します。秘密値はモデルにも画面にも出しません。

access_kind例runner の処理人がテストするとき
none公開ステージング何もしないURL を開くだけ
cf_accessstaging https://staging.shop.example.comSecrets Store の access_secret_ref から Client ID / Secret を取り出し、CF-Access-Client-Id / CF-Access-Client-Secret を対象オリジンへのリクエストにだけ付ける（extraHTTPHeaders ではなく route で付与し、他ドメインに漏らさない）社内アカウントで Access ログイン（S09 に手順を表示）
basicuat https://uat.shop.example.comhttpCredentials を設定S09 の「ログイン情報を表示」で確認（閲覧ログを記録）
ip_allowlist社内ネットワーク限定の環境Browser Rendering の送信元 IP は固定ではないため、原則使わない。必要なら対象側を Access 保護に切り替えるVPN 接続などの手順を entry_guide_md に書く
  • テストアカウント（fixture kind = account）のパスワードも Secrets Store に置き、fixture_versions.secret_ref に参照名だけを保存します。
  • エージェントが入力するときは、モデルには {{FX-11.password}} というプレースホルダだけを見せ、fill ツールの実行時に runner が置き換えます（AI ネイティブ設計）。
  • 証拠のスクリーンショットでは、type=password の入力欄とフィクスチャで「マスク」指定した要素を塗りつぶしてから保存します。

実行パイプライン

実行（runs）は手動・エージェント・スクリプトのどれでも同じ行で表します。ブラウザを使うのは agent / script / hybrid の機械実行部分だけで、manual は web 上で人が進めます。

sequenceDiagram
  participant W as web
  participant Q as Queue
  participant R as runner
  participant WF as RunWorkflow
  participant BR as Browser Rendering
  participant T as 対象環境
  participant AI as AI Gateway / Claude
  participant D as D1 / R2
  W->>D: runs を作成（state = queued）
  W->>Q: { run_id }
  Q->>R: メッセージ（並列度 max_concurrency）
  R->>WF: create(run_id)
  WF->>D: step 1 準備: TC バージョン・フィクスチャ版を解決し fixture_versions_json に固定
  WF->>T: step 2 リセットフック（reset_hook_json）とシード投入
  WF->>BR: step 3 ブラウザ起動（認証情報を設定）
  loop 各ステップ
    WF->>BR: 操作（script または エージェント）
    BR->>T: 画面操作
    WF->>AI: エージェントの次の行動（agent / hybrid のみ）
    WF->>D: step 4 証拠を R2 に保存、run_steps を更新
  end
  WF->>AI: step 5 ジャッジ（llm）
  WF->>D: step 6 判定ポリシーで verdict を確定（state = completed）
  WF->>W: step 7 通知（アサイン者・Slack）と GitHub Check Run / Issue

Workflow のステップとリトライ

ステップ内容タイムアウトリトライ失敗時
prepareTC バージョンとフィクスチャ版の解決。runs.fixture_versions_json に固定30 秒3 回（指数）state = error
reset環境のリセットフック・シード投入（HTTP 呼び出し）2 分2 回verdict = blocked（理由: 前提データの準備に失敗）
browseブラウザ起動とステップ実行。ステップごとに証拠を保存全体 15 分 / 1 操作 30 秒ブラウザ起動のみ 2 回途中までの証拠を残し verdict = blocked または fail（ジャッジに回す）
judgeassert / visual / llm ジャッジ2 分3 回（429 / 5xx のみ）verdict = needs_review
finalize判定ポリシー適用、plan_items.latest_run_id 更新、監査ログ30 秒3 回state = error
notify通知と GitHub 反映1 分5 回結果は確定済み。通知だけ失敗として記録
  • Workflow のステップは冪等にします（同じ run_id と seq で上書き）。
  • キャンセルは web から service binding 経由で Workflow インスタンスを terminate し、runs.state = error、verdict = skipped にします。
  • 計画の一括実行（例: PLAN-4 の agent 対象 31 件）は 1 件ずつ Queue に入れ、max_concurrency で同時ブラウザ数を抑えます。

コストの大部分はエージェント実行

安定した TC は script モードへ移す（AI が実行ログから Playwright スクリプトを提案）ことで、エージェント実行の件数を減らします。プロジェクトごとの月次上限を projects.settings_json.ai_budget_usd で設定し、超えたら agent 実行を止めて manager に通知します。

監査・バックアップ・保持

  • 監査ログ: 仕様・計画・フィクスチャ・判定・権限の変更はすべて activity_log に差分付きで記録。ログイン情報の閲覧（S09）も記録します。
  • バックアップ: D1 Time Travel（30 日以内の任意時点に戻せる）に加え、毎日 wrangler d1 export 相当のエクスポートを R2 の別バケット indx-watch-backup に保存（90 日保持）。
  • データ保持: 証拠ファイル（evidence/）は R2 ライフサイクルで 180 日後に削除。D1 の evidence 行は残し「期限切れ」と表示。リリースの最終結果に使われた証拠は retain フラグで保持期間外にできます。フィクスチャとベースラインは削除しません。
  • 可観測性: Workers Observability（ログ・トレース）と AI Gateway のログを使い、独自の監視基盤は作りません。

環境とデプロイ

環境用途Cloudflare リソース認証
local開発wrangler dev のローカル D1 / R2（Miniflare）。Browser Rendering は --remote 時のみDEV_USER_EMAIL で疑似ログイン
stagingINDX Watch 自体の検証名前に -staging を付けた別リソース（D1・R2・Queue）Access（開発者のみ）
production社内・顧客が使う本番上記のリソース一覧Access（社内ドメイン + 招待顧客）

デプロイ手順（GitHub Actions）

  1. main への push で CI: pnpm install → 型チェック → vitest → opennextjs-cloudflare build。
  2. staging へ: wrangler d1 migrations apply indx_watch-staging --remote → wrangler deploy --env staging（runner → web の順）。
  3. staging で INDX Watch 自身のスモーク計画を実行（INDX Watch で INDX Watch をテストする）。
  4. タグ watch-v* の push で production へ同じ手順を実行。D1 マイグレーションは手動承認（GitHub Environments の required reviewers）を挟む。

Cloudflare API トークンは GitHub の Environment secret に置き、権限は Workers / D1 / R2 / Queues の編集に絞ります。

主要な設計判断

ADR-001

Next.js + OpenNext で Workers に載せる

決定: UI と API を 1 つの Next.js（App Router）にまとめ、@opennextjs/cloudflare で Worker にする。

理由: Server Components と Server Actions で API 層を別に書かずに済み、コード量が最も少ない。Workers のバインディング（D1 / R2 / Queue）をそのまま使える。

代わりに諦めること: Node 専用ライブラリの一部。ブラウザ操作など重い処理は runner に分ける。

ADR-002

実行は Cloudflare Workflows

決定: 1 実行 = 1 Workflow インスタンスとし、準備・操作・ジャッジ・確定をステップに分ける。

理由: 数分かかる処理を途中から再開でき、ステップ単位のリトライとタイムアウトが標準で付く。状態管理を自前で書かなくてよい。

代わりに諦めること: ステップ間で渡せるデータは小さくする（大きなものは R2 に置いてキーだけ渡す）。

ADR-003

v1 では Durable Objects を使わない

決定: 実行中の進捗はポーリング（2 秒間隔、実行中の画面のみ）で表示する。

理由: リアルタイム共同編集やロックの要件が v1 にはない。DO を入れると状態の置き場所が D1 と二重になる。

見直す条件: 実行ビューアのライブ配信や同時編集が必要になったとき。

ADR-004

D1 を唯一の正にする

決定: 仕様・計画・結果は D1 が正。リポジトリへの YAML 書き出しは M3 以降に「エクスポート」として提供し、取り込みは AI 仕様取り込み経由とする。

理由: ビジネス職がブラウザで編集でき、実行結果と同じ DB で結合できる。リポジトリと DB の双方向同期は衝突処理のコストが大きい。

ADR-005

エージェントは Playwright の自前ツールで操作する

決定: Claude の computer use ではなく、a11y ツリーの ref を使う自前ツール（navigate / click / fill など）で操作する。

理由: DOM を直接扱えるので座標推定より安定し、トークンが少なく安い。操作ログがそのまま Playwright スクリプトに変換できる。

例外: canvas 中心の UI だけ computer_toolset_20260801 を検討する。

ADR-006

LLM 呼び出しは AI Gateway 経由

決定: Anthropic SDK の baseURL を AI Gateway に向ける。

理由: 呼び出しログ・コスト集計・レート制限を自前で作らずに済む。
