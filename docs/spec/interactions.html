ER・通信フロー

データベースの全テーブルの関係と、人・システムがどの順番で何と通信し、どのテーブルに書き込むかを図でまとめます。テーブル定義の正は データモデル、構成の正は アーキテクチャ です。このページはその 2 つをつなぐ「地図」です。

状態 ドラフト v0.1更新 2026-11-19対象 データモデル v0.2（35 テーブル + 全文検索の仮想テーブル 1）関連 認証・行動ログ · 多言語

読み方

図の凡例

実線の矢印
同期の呼び出し（応答を待つ）。HTTP、service binding、D1 / R2 バインディング。
点線の矢印
非同期・イベント。Queue、Workflow のイベント、Logpush、R2 イベント通知、Webhook。
ER の記号
||--o{ は「1 対 0 以上」、||--|{ は「1 対 1 以上」、}o--o{ は「多対多」、|o--o| は「0/1 対 0/1」。
キー
PK 主キー、FK 外部キー、UK 一意キー。ER には主要な列（キー・状態・種別）だけを載せる。

ER 図（詳細）

35 テーブルを 6 つの領域に分けて描きます。領域をまたぐ関係は、両方の図に相手のテーブルを「キーだけ」で載せています。すべてのテーブルは {prefix}_{ULID} の id を主キーに持ち、物理削除はしません（archived_at）。そのため「削除時の扱い」は、親をアーカイブしたときに子がどうなるかを書いています。

ライフサイクルの連鎖

仕様を書いてからリリースを判定するまでに、どの出来事がどのテーブルを更新するかを 1 本の流れで示します。

flowchart TD
  A["UC と AC を書く / AI 取り込み"] -->|"use_cases, acceptance_criteria, translations"| B["TC を作る"]
  B -->|"test_cases, test_case_versions, test_case_criteria"| C["承認して ready"]
  C -->|"test_cases.status, activity_log"| D["計画に追加・担当決定"]
  D -->|"test_plans, plan_items"| E["デプロイを受信"]
  E -->|"deployments"| F["実行を開始"]
  F -->|"runs, run_steps（手順をコピー）"| G["ステップを実行"]
  G -->|"run_steps, evidence, page_views"| H["ジャッジ"]
  H -->|"judgements"| I{"判定ポリシー"}
  I -->|"pass / fail / blocked"| J["実行を確定"]
  I -->|"needs_review"| K["レビュー待ち"]
  K -->|"judgements（human）"| J
  J -->|"runs.verdict, plan_items.latest_run_id / status"| L["完了計算"]
  L -->|"AC → UC の状態（計算のみ、保存しない）"| M["リリース判定"]
  M -->|"releases.status, approved_by, activity_log"| N["Go / No-Go"]
  J -.->|"fail のとき"| O["GitHub Issue"]
  O -.->|"issues"| M
保存するもの・計算するもの

AC・UC の状態と網羅率、リリースのゲート判定は保存せず、毎回 packages/core の純粋関数で計算します。保存するのは「起きたこと」（実行・判定・承認）だけです。こうすると、閾値を変えても過去のデータを書き換えずに再計算できます。

送信元送信先方式認証運ぶデータ同期
ブラウザAccess → webHTTPSAccess セッション（CF_Authorization）→ Cf-Access-Jwt-Assertion を jose で検証画面表示、Server Actions同期
ブラウザR2HTTPS（署名付き URL、10 分）web が発行した署名スクリーンショット、フィクスチャのアップロード同期

整合性とトランザクション

D1 の batch で 1 単位にするもの

D1 は複数の SQL を batch() でまとめて実行でき、途中で失敗すると全体が取り消されます。次の組み合わせは必ず 1 つの batch にします。

操作同じ batch に入れるもの
表示キーの採番UPDATE project_counters SET next_value = next_value + 1 ... RETURNING と、その番号を使う行の INSERT
TC の新しい版test_case_versions の INSERT、test_cases.current_version_id の UPDATE、activity_log
フィクスチャの新しい版fixture_versions、fixtures.current_version_id、activity_log（R2 への PUT は先に済ませる）
実行の開始runs、全 run_steps、plan_items.status
実行の確定runs.state / verdict、plan_items.latest_run_id / status、activity_log
AI 提案の採用作成する UC・AC・TC・版・リンクすべて、ai_suggestions.status、activity_log

冪等キー（リトライで二重にしない）

入口冪等キー重複したとき
GitHub WebhookX-GitHub-DeliveryKV ではなく D1 の activity_log（action = github.delivery, target_id = delivery id）で確認し、既にあれば 200 を返して何もしない
Access ログの取り込みray_id + action（access_events の UNIQUE）INSERT ... ON CONFLICT DO UPDATE（GraphQL の補完列だけ更新）
実行ジョブ（Queue）Workflow の instance id = run_id同じ id の Workflow は作成できないので、2 通目のメッセージは無視される
Workflow のステップステップ名（Workflows が結果を保存）再実行時は保存済みの結果を使う。D1 への書き込みは run_steps (run_id, seq) の UNIQUE で守る
テストメールMessage-IDevidence に同じ R2 キーがあれば無視
翻訳ジョブ(entity_type, entity_id, field, locale) + source_hash同じハッシュの翻訳が既にあれば呼び出さない
ログインセッションidentity_nonce同時に届いたリクエストで二重に作らないよう INSERT ... ON CONFLICT DO NOTHING のあとで読み直す
Server Actions（二重クリック）フォームに埋めた ULID同じ ULID の行があれば既存を返す

順序と書き込みのルール

  • R2 が先、D1 が後。ファイルを置いてから参照行を作る。逆にすると「参照先のないファイル」ではなく「ファイルのない参照」ができ、画面が壊れる。孤立したファイルは週次で掃除する。
  • 判定は追記のみ。judgements と activity_log は UPDATE しない。runs.verdict は判定の列から再計算できる「結果のキャッシュ」。
  • 同時編集。UC・TC・フィクスチャの編集画面は読み込んだ時点の updated_at（版は current_version_id）を送り、違っていれば保存せず「他の人が更新しました」と差分を出す（楽観ロック）。
  • runner は web を経由せず D1 に書く。ただし権限チェックが要る書き込み（人の判定）は web だけが行い、runner へは sendEvent で結果だけ渡す。
  • 時刻。すべて UTC ミリ秒。Access ログの CreatedAt も UTC に変換して occurred_at に入れる。
