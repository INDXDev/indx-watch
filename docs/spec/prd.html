SPEC-01 · PRD

INDX Watch プロダクト要求仕様

INDX Watch は、ビジネス職・エンジニア・QA の誰もが同じ場所でテスト仕様を書き、実行し、証拠付きで合否を残せる、AI ネイティブな E2E テスト / QA 管理プラットフォームです。Cloudflare 上にセルフホストし、社内と招待した顧客だけが使います。

状態 ドラフト v0.1更新 2026-11-19オーナー QA リード関連 ドメインモデル · UX・ユーザーフロー

背景と課題

現在、リリース前の QA は「スプレッドシートの手順書」「Slack のスレッド」「各自のスクリーンショットフォルダ」で回っています。テストそのものより、準備と確認と報告に時間がかかっています。

課題いま起きていること影響
仕様が散らばっているユースケースと完了条件が PRD・チケット・スプレッドシートに分散し、最新版が分からない「どこが・どうなれば完了か」を毎回人に聞く
環境への入り方が属人的staging の URL、Access の通し方、テストアカウントのパスワードが特定の人の頭の中にある新しいテスターが最初の 1 件を実行するまで半日かかる
テストデータが管理されていないクーポン CSV や会員アカウントが共有ドライブで上書きされ、履歴がない「前回は通ったのに」の原因がデータか実装か切り分けられない
誰が何をやるか追えないアサインがチャットで行われ、期限と重要度が記録されないリリース直前に P0 の未実行が見つかる
証拠が残らない合否だけが記録され、スクリーンショットや実行したバージョンが紐づかない不具合の再現と Go/No-Go 判断の根拠が弱い
道具が職種ごとに違うエンジニアは Playwright、QA はスプレッドシート、顧客 UAT はメール往復結果を手で集計し直す
AI の使い方が決まっていないブラウザエージェントや LLM 判定を試したいが、判定の根拠と人のレビューをどう残すか決まっていないAI の結果を信用してよいか判断できない

目的とゴール

目的は「リリースのたびに、何がテスト済みで何が残っているかを、証拠付きで誰でも答えられる状態」を作ることです。すべての情報を D1 の 1 つのデータモデルにつなげ、AI が仕様作成・実行・判定を手伝い、人が承認します。

大事にしていること

機能の取捨選択や UI の判断で迷ったら、この 7 つに照らして決めます。具体的な UI ルールは UX 原則 にあります。

1. 迷わない

どの画面にも「次にやること」が 1 つだけ強調表示されます。テスターはマイタスクを開けば、環境 URL、入り方、テストアカウント、使うフィクスチャ、手順が 1 画面にそろっています。探す行為をなくすことが最優先です。

2. 誰でも QA できる

手順は平易な日本語で、1 ステップに 1 動作だけ書きます。セレクタやコードを書かなくてもテストケースを作れ、実行できます。エンジニア向けの Playwright スクリプトは任意の上乗せです。

3. 完了の定義が明確

すべてのユースケースは完了条件（AC）を持ち、AC はテストケースで網羅されます。「完了」は人の感覚ではなく、AC の網羅状況と最新の判定から計算されます。

4. 証拠ベース

合否には必ずスクリーンショットなどの証拠と判定理由が付きます。証拠のない pass は記録できません（スキップを除く）。

5. AI は提案、人が承認

AI が作った仕様は origin = ai・draft で入り、人の承認で ready になります。AI の判定は信頼度付きで、閾値（既定 0.8）未満は人のレビューキューに回ります。

6. すべて履歴が残る

テストケースとフィクスチャはバージョン管理され、実行は「どの仕様の版・どのデータの版で・どのデプロイに対して」行ったかを必ず記録します。変更は activity_log に残ります。

7. コードは少なく

Next.js 1 アプリとランナー Worker 1 つで作ります。D1 / R2 / Browser Run（旧 Browser Rendering）/ Workflows / Queues / Access など Cloudflare のマネージド機能に任せ、自前実装を増やしません。

非機能要件

ID区分要件
NFR-01アクセス制御アプリ全体を Cloudflare Access の背後に置く。Worker は全リクエストで Cf-Access-Jwt-Assertion を検証し、メールアドレスで users と照合する。未登録ユーザーは 403。例外は /api/github/webhook（HMAC 署名で検証）のみ
NFR-02権限ロール（admin / manager / tester / guest）とプロジェクトメンバーシップで認可する。guest は自分の計画アイテムとその実行に必要なデータ以外を API レベルで取得できない
NFR-03秘密情報テストアカウントのパスワード、環境のサービストークン、API キーは D1 に平文で保存しない。D1 には参照名（secret_ref）のみ、値は Workers Secrets / Secrets Store に置く。画面ではマスク表示し、表示操作は監査ログに残す
NFR-04監査ログ作成・更新・削除・判定・承認・秘密の表示を activity_log に actor・対象・差分付きで記録する。ログは削除しない
NFR-05AI の追跡性AI の生成物と判定には、モデル名・プロンプトのバージョン・入力の参照を保存する。人の承認なしに ready や最終確定にしない
NFR-06コストLLM 呼び出しは AI Gateway 経由にし、プロジェクトごとの月間上限（既定 USD 300、未決）を設ける。上限の 80% で manager に通知し、100% で agent 実行を停止して手動に切り替える。実行ごとのコストを runs.cost_json に残す
NFR-07性能一覧画面の表示は p95 で 1 秒以内（D1 クエリ 1 画面 5 本以内）。手動ランナーの判定保存は 300ms 以内。エージェント実行は 1 TC あたり中央値 3 分以内を目標とし、15 分の上限を超えたら blocked（AI ネイティブ設計の実行上限）
NFR-08同時実行エージェント実行は Queues で流量を制御し、Browser Run の同時ブラウザ数の上限内で動かす（既定 同時 4。料金の無料枠「同時数の月平均 10」以内に収める）。超過分は queued で待つ
NFR-09データ保持実行メタデータと判定は無期限。スクリーンショットなどの証拠は 180 日、ただしリリースの Go 判定に使われた実行の証拠は無期限（R2 のライフサイクルとタグで制御）。フィクスチャの版は削除しない
NFR-10可用性Cloudflare のマネージドサービスの SLA に従う。ランナーは Workflows で各ステップを再試行可能にし、途中で落ちても再開できる
NFR-11アクセシビリティキーボードのみで実行画面を操作できる。判定は色だけでなくラベルで示す。WCAG 2.2 AA を目標
NFR-12レスポンシブマイタスクと手動ランナーは幅 375px のスマートフォンで操作できる。管理系画面はデスクトップ優先
NFR-13テスト対象への影響エージェントは登録された環境のベース URL 配下以外に遷移しない。prod 種別の環境では書き込みを伴う TC を実行できない設定を既定にする

スコープ外

  • 負荷試験・性能試験（k6 などの専用ツールを使う）
  • ネイティブモバイルアプリ（iOS / Android）の実機テスト。モバイル幅の Web 表示は対象
  • 本番環境の常時監視・死活監視（外形監視サービスを使う）
  • ユニットテスト・API 単体テストの管理（各リポジトリの CI に任せる）
  • 汎用のチケット管理。不具合は GitHub Issue に起票し、INDX Watch はリンクを持つだけ
  • 社外向け SaaS としての提供、マルチテナント課金
  • セキュリティ診断・脆弱性スキャン
