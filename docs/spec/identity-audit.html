SPEC-09 · 認証・行動ログ

認証・行動ログ（誰が・いつ・どこで・どう作業したか）

一番の目的は、すべてのテスト作業と判定が、Google Workspace（社員）または招待メール（顧客）の ID と確実に対応していることです。Cloudflare Access の ID 情報と Cloudflare の各種ログを組み合わせ、テスターごとに「どの方法でログインし、どこから、どの端末で、いつ何をしたか」を記録します。Worker まで届かない失敗ログインも Access のログから取り込みます。

状態 ドラフト v0.2更新 2026-11-19仕様の確認日 2026-11-19関連 データモデル · アーキテクチャ · S12 ログイン・作業履歴

目的

  • 証跡: テスト結果の信頼性を示すため、「誰が・いつ・どの環境で・どの端末から」判定したかを後から説明できるようにする。顧客の受け入れテスト（UAT）の合否も同じ扱い。
  • セキュリティ: 社外の人（顧客・委託テスター）が使うので、想定外の場所・端末からのログイン、拒否されたログイン試行、権限外の閲覧に気づけるようにする。
  • 作業の記録: ログとして残すだけ。テストにかかった時間の集計は計画の見積もりに使う程度で、人事評価には使わない（決定。プライバシー参照）。作業セッションの集計（work_sessions）は M4 の任意機能。

取れないもの

設計の前提として、Cloudflare からは取れない情報を明確にしておきます。

取れないもの理由対応
使った MFA の方式（パスキー、TOTP など）JWT・get-identity・ログのどのスキーマにも MFA 方式の項目がない社員は IdP 側で MFA を必須にし、IdP の監査ログと突き合わせる。顧客は Access の Independent MFA かパスキーを必須にする（方式は記録できないが、通過したことは保証される）
OTP のコードを入力しなかった試行Access の OTP ログはコード入力後にしか記録されない記録できない前提で扱う
WARP を入れていない端末の詳細（OS のバージョン、シリアル）端末情報は WARP 経由でのみ取れるUser-Agent の解析結果（ブラウザ・OS・端末種別）で代用。顧客には WARP を求めない
都市より細かい位置request.cf の緯度経度は IP からの推定で精度が低い保存するのは国・地域・都市・ASN まで。緯度経度は保存しない

ログインの記録

Access を通過したリクエストは、web Worker の最初の処理（ミドルウェア）で必ず以下を行います。Worker の公式ヘルパー ctx.access は Static Assets を持つ Worker では渡されないため使わず、jose で JWT を検証します。

// apps/web/lib/auth.ts（要点のみ）
const JWKS = createRemoteJWKSet(new URL(`https://${env.TEAM_DOMAIN}/cdn-cgi/access/certs`));

export async function authenticate(req: Request, env: Env): Promise<AuthContext> {
  const token = req.headers.get("Cf-Access-Jwt-Assertion");
  if (!token) throw new Unauthorized("Access を経由していません");
  const { payload } = await jwtVerify(token, JWKS, {
    issuer: `https://${env.TEAM_DOMAIN}`,
    audience: env.POLICY_AUD,
  });
  const ctx = requestContext(req);            // ip, rayId, cf.country/city/region/asn/asOrganization/colo/timezone, ua
  const session = await upsertLoginSession(env, payload, ctx, req); // 新規なら get-identity を 1 回呼ぶ
  return { user: session.user, loginSessionId: session.id, ...ctx };
}
  • セッションの区切り: identity_nonce が変わったら新しい login_sessions 行。同じ nonce で iat が変わった場合（再認証）も新しい行にし、前の行は end_reason = 'replaced'。
  • IP の変化: セッション中に IP が変わったら ip_changes を増やし、activity_log に auth.ip_changed を記録（モバイル回線の切り替えなどで起きるので、それだけでは警告にしない）。
  • 書き込み頻度: last_seen_at の更新は 1 分に 1 回までにして D1 の書き込みを抑える。
  • サービストークン（MCP など）: auth_kind = 'service_token'。トークンの持ち主（発行した人）を users の agent 行に紐づける。
  • 初回ログイン: 記録内容の告知を表示し、同意すると users.privacy_ack_at を保存。同意するまで他の画面は使えない。

失敗・拒否ログイン

Access に拒否されたリクエストは Worker に届きません。Access の認証ログを 3 つの経路で取り込み、access_events に集めます。ray_id と action の組で重複を除きます。

flowchart LR
  ACC["Cloudflare Access 認証ログ"] -- "Logpush（数分ごと）" --> R2["R2 cf-logs/access_requests/"]
  R2 -- "イベント通知" --> Q["Queue: log-ingest"]
  Q --> IW["runner Worker: 取り込み"]
  ACC -. "REST（1 時間ごと・補完）" .-> IW
  ACC -. "GraphQL（1 日 1 回・列の補完）" .-> IW
  IW --> D1[("D1 access_events")]
  IW --> CUR[("ingest_cursors")]
  D1 --> S12["S12 ログイン・作業履歴"]
  D1 --> AL["異常検知 → Slack 通知"]
  1. Logpush（正の経路）: access_requests を R2 の cf-logs/access_requests/ に出力。R2 のイベント通知で Queue に流し、NDJSON（gzip）を解析して挿入。元ファイルの場所は raw_r2_key に残す。
  2. REST（補完）: Workflow の定期実行で 1 時間ごとに GET /accounts/{id}/access/logs/access_requests?since=… を呼ぶ。続きの位置は ingest_cursors。Logpush が使えないプランや停止時にも欠けないようにする。プランによってはログ保持が 24 時間なので、間隔は 24 時間を超えないこと。
  3. GraphQL（列の補完）: 1 日 1 回 accessLoginRequestsAdaptiveGroups を取得し、approving_policy_id・has_warp・device_id を埋める。
  4. ユーザーとの突き合わせ: access_user_uid → users.access_sub、なければメールで照合。未登録のメール（招待していない人の OTP 試行など）は user_id = null のまま残し、S12 で目立たせる。
取り込みの監視

ingest_cursors の更新が 3 時間止まったら manager と admin に通知します。S12 には「最終取り込み時刻」を常に表示します。

作業時間と作業セッション

  • 表示時間: ブラウザが画面の表示中（タブが前面、かつ直近 2 分以内にマウス・キー操作あり）の時間を数え、画面を離れるときと 60 秒ごとに navigator.sendBeacon で送る。page_views.visible_ms を更新する。
  • 実行の操作時間: S05 では同じ仕組みをステップ単位で数え、run_steps.active_ms と runs.active_ms に保存する。「どのステップで時間がかかったか」が分かる。
  • 作業セッション: ユーザーごとに page_views と activity_log を時刻順に並べ、15 分以上の空白で区切る。区切りごとに開始・終了・操作時間・触ったプロジェクト・実行した RUN・場所・端末を work_sessions に保存する。1 時間ごとに直近分を再計算する。
  • 細かい生データ（ビーコン 1 回ごと）は D1 に入れず、集計値だけを保存する。傾向分析が必要になったら Analytics Engine（保持 3 か月）に送る。

Cloudflare 側の設定

  1. Zero Trust 組織: チームドメインを決める（例: indx.cloudflareaccess.com）。グローバルのセッション時間は 24 時間（既定）のまま、アプリ・ポリシー単位で上表の時間にする。
  2. IdP: 社員用に Google Workspace を追加（決定）。顧客用に One-time PIN を手動で追加（2026-06 以降の新規アカウントは既定が Cloudflare IdP のため）。
  3. Worker を保護: web Worker に Access を付ける（Worker 単位の保護。カスタムドメイン・workers.dev・Preview URL がまとめて保護される）。ポリシー: 社員ドメインを許可 / 顧客は個別メールで許可＋Independent MFA。
  4. Webhook パス: /api/github/webhook だけ専用の Access アプリで Bypass。Worker 単位の保護との優先関係は M1 で検証する。
  5. Logpush: アカウントの Logpush ジョブを作成し、access_requests（必須）、audit_logs_v2（推奨）、device_posture_results（WARP を使う場合）を R2 バケットの cf-logs/ に出力。
  6. R2 イベント通知: cf-logs/access_requests/ の object-create を Queue log-ingest に送る。
  7. API トークン: 用途ごとに分けて Secrets Store に保存（下表）。
  8. AI Gateway: Access の ID が cf.user_id として記録されることを確認し、cf-aig-metadata に project_key・run_id・feature を付ける。

プライバシーと保持

IP アドレス・場所・作業時間は個人に関する情報です。個人情報保護法に沿って、目的・閲覧できる人・保持期間を決め、利用者に告知します。顧客（guest）には契約時にも説明します。

項目決定
利用目的テスト結果の証跡、不正アクセスの検知、テスト計画の工数見積もり。人事評価には使わない。
告知初回ログイン時に記録する項目と目的を表示し、同意を users.privacy_ack_at に保存。内容を変えたら再同意。
閲覧できる人admin: すべて。manager: 自分のプロジェクトのメンバーの作業サマリ（作業時間・実行数）のみで、IP と都市は見えない。tester / guest: 自分のログイン履歴のみ。
閲覧の記録S12 を開く・書き出すたびに audit.viewed / export.downloaded を記録。
保持activity_log と access_events は 3 年、login_sessions と work_sessions は 2 年、page_views は 1 年。Logpush の元データは R2 に 3 年。
最小化緯度経度は保存しない。IP は 1 年を過ぎたら末尾を削る（IPv4 /24、IPv6 /48）。AI Gateway には秘密を含む本文を保存しない（cf-aig-collect-log-payload: false）。
本人からの請求本人は S12 で自分の記録を見られ、CSV で書き出せる。削除の請求は admin が対応し、証跡として必要な行は匿名化で対応する。

M1 で確かめること

  • Zero Trust のプラン（Free / Standard）で access_requests の Logpush が使えるか。使えなければ REST の取り込み間隔を短くする。
  • GraphQL の accessLoginRequestsAdaptiveGroups の保持期間とプラン要件。
  • get-identity のレート制限（ログインごとに 1 回なら問題ない想定）。
  • Worker 単位の Access 保護と、パス単位の Bypass アプリの優先関係。
  • vinext のビルドで Static Assets が付き、ctx.access が使えないこと（使えたとしても jose 検証は残す）。
  • ユーザー API を読むための API トークン権限の正式名。
  • Audit Logs v2 に Access ポリシーの変更が含まれるか。
