SPEC-03 · UX・ユーザーフロー

UX 原則とユーザーフロー

誰が、どの画面から入り、何をすればテストが終わるのかを定義します。画面ごとの詳細なモックと受け入れ基準は第 2 層の 画面ドキュメント（S01〜S12） にあります。

状態 ドラフト v0.1更新 2026-11-19関連 PRD · ドメインモデル · AI ネイティブ設計

UX 原則

PRD の「大事にしていること」を、画面を作るときに守る具体ルールに落としたものです。レビューではこの表のルール ID で指摘します。

IDルール具体的には
UX-01「次の一手」を常に 1 つ出す各画面の右上に主ボタン（.btn.primary）を 1 つだけ置く。マイタスクなら「次のテストを始める」、リリース準備状況なら「残りの P0 を割り当てる」。主ボタンが 2 つある画面は作らない
UX-023 クリック以内でテスト実行へどの画面からでも、自分の担当 TC の実行画面まで 3 クリック以内。マイタスク → 「実行」で 1 クリック
UX-03手順は 1 ステップ 1 動作「ログインしてカートに入れる」は 2 ステップに分ける。AI が下書きした手順も自動で分割を提案する
UX-04入り方を常に見せる実行画面の上部に、環境名・URL（クリックで新しいタブ）・入り方・テストアカウント（コピーボタン付き、パスワードはマスク）を固定表示する
UX-05証拠は貼り付けで添付実行画面では Ctrl/⌘ + V でクリップボードの画像を現在のステップに添付する。ドラッグ＆ドロップとファイル選択も使える。スマホではカメラロールから選ぶ
UX-06AI の出力は見た目で分けるAI が作ったもの・判定したものには必ず紫系の AI 表示（AI / .ai-box）と信頼度（0.00〜1.00）を付ける。人が承認すると通常の表示に変わる
UX-07状態は色とラベルの両方で判定は 合格 不合格 のように色付きラベルで示し、色だけに頼らない
UX-08完了は計算で示すユースケースとリリースには「AC 3 件中 2 件合格」のように分母付きで進捗を出す。手入力の進捗率は持たない
UX-09版を意識させない、でも必ず残す編集は普通に保存するだけで新しい版になる。版の一覧と差分は「履歴」タブに置き、実行結果には使った版を小さく表示する
UX-10空の画面にしないデータがない画面には、何が表示されるかと最初の 1 件を作る操作を表示する（例: 「ユースケースがまだありません。PRD を貼り付けて AI に下書きさせる」）
UX-11確認ダイアログより取り消し削除・アサイン変更は即時反映し、5 秒間「元に戻す」を出す。取り消せない操作（Go 判定・ベースライン承認）だけ確認を挟む
UX-12判定を覆すときは理由必須AI の判定を人が変える、ベースラインを更新する、要確認を確定する操作には理由の入力欄を必須にする

情報設計

ナビゲーションは「自分」「プロジェクト」「AI」の 3 グループです。全画面で左ナビの並びは同じで、現在地だけを強調します。プロジェクトは URL の [key]（例: SHOP）で切り替えます。

flowchart LR
  root["/ マイタスク"] --> review["/review レビュー待ち"]
  root --> p["/p/SHOP プロジェクト"]
  p --> rel["releases/v2.4.0 リリース準備状況"]
  p --> specs["specs 仕様ツリー"]
  specs --> tc["tc/128 テストケース"]
  specs --> imp["specs/import AI 仕様取り込み"]
  p --> plans["plans/4 テスト計画"]
  p --> runs["runs/1032 実行結果"]
  runs --> exec["runs/1029/execute 手動ランナー"]
  p --> fx["fixtures フィクスチャ"]
  p --> env["environments 環境"]
  p --> dep["deployments デプロイメント"]

URL の規則

  • プロジェクト配下はすべて /p/[key]/...。表示キーの番号部分を URL に使う（TC-128 → /p/SHOP/tc/128）。内部 ID（ULID）は URL に出さない。
  • 個人に紐づく画面はプロジェクト横断でルート直下（/、/review）。
  • 一覧のフィルタはクエリ文字列（?priority=P0&verdict=fail）で表し、URL を共有すれば同じ表示になる。
  • 外部向けは /api/...（GitHub Webhook・ランナーのコールバック）と /mcp のみ。

guest の見え方

guest のナビゲーションには「マイタスク」だけを出します。プロジェクト配下の一覧画面には遷移できず、API も plan_items.assignee_id = 自分 に紐づくデータだけを返します。

主要ユーザーフロー

各フローは「誰が・どの画面で・何をして・何が記録されるか」を示します。サンプルの人物とデータは全ドキュメント共通です。

テスターがアサインを受けて実行し、証拠を残す

主役: 田中 健（tester）/ 対象: TC-129 期限切れクーポンでエラーが出る（P1, manual）/ 画面: S01 → S05

flowchart TD
  A["通知: TC-129 が割り当てられました"] --> B["S01 マイタスクを開く"]
  B --> C["次のテストを始める"]
  C --> D["S05 手動ランナー: 環境 staging と入り方・アカウントを確認"]
  D --> E["ステップを 1 つずつ実行"]
  E --> F{"期待結果どおり?"}
  F -- はい --> G["合格 + スクリーンショットを貼り付け"]
  F -- いいえ --> H["不合格 + 証拠 + メモ"]
  F -- 前提が崩れている --> I["実行不可 + 理由"]
  G --> J{"最後のステップ?"}
  H --> J
  I --> K["実行終了: blocked"]
  J -- いいえ --> E
  J -- はい --> L["実行を完了: 最終判定を記録"]
  L --> M["S01 に戻り次のタスクへ"]
  1. アサイン通知（アプリ内・メール）から、または朝に S01 マイタスク を開く。担当アイテムは優先度 → 期限順に並ぶ。
  2. 「次のテストを始める」を押すと runs が作られ（state = running、使う TC の版・デプロイメント・フィクスチャの版を固定）、S05 に移る。
  3. 画面上部で環境 staging（https://staging.shop.example.com）、入り方、テストアカウント FX-11 を確認する。クーポンデータ FX-3（v4）の該当行もここに出る。
  4. ステップごとに操作し、合格・不合格・実行不可を選ぶ。証拠は貼り付けで添付し、run_steps と evidence に保存される。
  5. 最後のステップで「実行を完了」を押すと最終判定（human ジャッジ）が judgements に入り、plan_items.status = done になる。不合格なら 失敗フロー へ。

QA リードがテスト計画を作り、アサインし、Go/No-Go を判断する

主役: 佐藤 美咲（manager）/ 対象: リリース v2.4.0、PLAN-4 v2.4.0 リグレッション（86 件）/ 画面: S08 → S02 → S06

flowchart TD
  A["リリース v2.4.0 を作成 (GitHub release か手動)"] --> B["S08 テスト計画を作成"]
  B --> C["対象 TC を追加: P0/P1 全件 + AI の影響分析"]
  C --> D["AI 提案: 担当と環境の割り振り案"]
  D --> E["案を調整して一括アサイン (人 / Watch Agent)"]
  E --> F["テスト期間: S02 で進捗を毎日確認"]
  F --> G{"P0 の未実行・要確認がある?"}
  G -- はい --> H["S06 レビューキューで確定 / 再アサイン"]
  H --> F
  G -- いいえ --> I{"Go 条件を満たす?"}
  I -- はい --> J["Go 判定 (理由付きで記録)"]
  I -- いいえ --> K["No-Go 判定 + 残課題を Issue 化"]
  1. S08 で v2.4.0 に対する計画 PLAN-4 を作る。P0/P1 を一括追加し、PR #482 の影響分析（ai_suggestions.kind = impact）で提案された TC を追加する。

  3. 案を調整して「選択した項目を割り当てる」。担当者に通知が飛ぶ。
  4. 期間中は S02 で「pass 52 / fail 4 / blocked 2 / 要確認 3 / 未実行 25」の内訳と P0 の残件を見る。
  5. Go 条件（既定: P0 全件合格、P1 合格率 95% 以上、P0/P1 の要確認 0 件、P0 の未網羅 AC 0 件）を満たしたら Go を記録する。判定は取り消せないので確認を挟む（UX-11）。

顧客がメール招待から自分の項目だけを実行する（UAT）

主役: 山本 様（guest・株式会社サンプル）/ 招待: 佐藤 美咲 / 環境: uat（https://uat.shop.example.com）/ 画面: S01 → S05

sequenceDiagram
  actor Lead as 佐藤 (QA リード)
  participant W as INDX Watch
  participant CF as Cloudflare Access
  actor Cust as 山本 様 (guest)
  Lead->>W: guest として招待 (メール・期限 2026-12-01)
  W->>CF: Access ポリシーにメールを追加
  W-->>Cust: 招待メール (UAT 3 件・期限)
  Cust->>CF: リンクを開きメールアドレスを入力
  CF-->>Cust: ワンタイム PIN をメール送信
  Cust->>CF: PIN を入力
  CF->>W: JWT 付きでアクセス
  W-->>Cust: S01 マイタスク (自分の 3 件のみ)

フィクスチャをブラウザでアップロード・編集し、差分を確認して戻す

主役: 田中 健 / 対象: FX-3 クーポンセット（dataset, CSV, v4）/ 画面: S07

flowchart LR
  A["S07 で FX-3 を開く (v4)"] --> B{"どう変える?"}
  B -- "CSV を差し替え" --> C["ファイルをドロップ"]
  B -- "その場で編集" --> D["表エディタで行を編集"]
  C --> E["検証: 列名・型・必須列"]
  D --> E
  E --> F["v4 との差分を表示 (追加 2 行・変更 1 行)"]

  G --> H["FX-3 を使う TC と計画中の実行に影響を表示"]
  H --> I{"問題が出た?"}

account 種別

テストアカウント（FX-11）のパスワードは版の本体に入れず、secret_ref で Secrets Store を参照します。画面ではマスク表示し、表示ボタンを押すと監査ログに記録されます。

失敗からトリアージ、GitHub Issue、修正デプロイ、再テストまで

書き方

  • ボタンは動詞で終える（「保存」ではなく「新しい版として保存」、「OK」は使わない）。
  • エラーは原因と直し方を書く（「CSV の 3 行目: discount_rate は 0〜100 の数値にしてください」）。
  • テスト手順は「〜する」で終える命令形ではなく、「クーポン欄に WINTER10 を入力する」のように操作と値を具体的に書く。
  • 期待結果は観察できる事実で書く（「割引額 −1,000 円が合計の上に表示される」）。「正しく動く」は使わない。
