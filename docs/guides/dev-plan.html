開発プラン

ドキュメントをどう運用するか、コンポーネントとファイルをどう分けるか、何をどの順に作るかを 1 ページにまとめます。タスクは ID 付きで、1 タスク = 1 PR の大きさに切ってあります。上から順に実行すれば M1 から M4 まで進められる状態を目指します。

状態 確定 v1.0（実行可能）更新 2026-11-19関連 実装ガイド · ER・通信フロー · データモデル

すぐ始めるには

  1. 人が準備する: M0.5 の H-01〜H-07（Cloudflare・Google Workspace・GitHub の設定）を行う。所要 半日。
  2. Claude Code に最初のタスクを渡す: 新しいセッションで 依頼テンプレート の T-101 を貼る。
  3. PR をレビューしてマージ: PR 説明のチェックリスト（タスクの完了条件）を確認する。
  4. 次のタスクへ: 依存関係の図 で着手できるタスクを選ぶ。依存のないタスクは別セッションで並行して進めてよい。
このページが「次に何をするか」の正

タスクの状態（未着手 / 進行中 / 完了）は GitHub の Issue で管理します。Issue のタイトルは T-101 モノレポ雛形 のようにタスク ID から始め、本文にこのページのタスク節へのリンクを貼ります。タスクの内容を変えるときは、先にこのページを直します。

更新のルール

  1. docs → コードの順。仕様が変わる PR では、最初のコミットで docs を、次のコミットでコードを変える。レビューは docs の差分から読む。
  2. テーブルを変えたら 4 点セット: packages/db/schema.ts・マイグレーション・data-model.html（必要なら interactions.html の ER 図も）・packages/bundle の型と portability.html の対応表を同じ PR で更新する。
  3. 画面を足すときはモックから: docs/screens/ に HTML を追加し、AGENTS.md の画面表、ux.html の画面一覧、index.html に載せる。
  4. Cloudflare の仕様は Web で確認: 前提にする機能・上限・料金は developers.cloudflare.com と changelog で確かめ、architecture.html の確認メモに日付と出典を追記する。
  5. 版と日付: 各ページの meta 行の「状態」（ドラフト vX.Y / 確定）と「更新」を変える。大きな変更は 変更履歴 に 1 行書く。
  6. ID は変えない: SPEC-xx、GUIDE-xx、Sxx、T-xxx、FR-xx は一度付けたら変えない。廃止したら「廃止」と書いて残す。
  7. 公開: docs/ はそのまま HTML アーティファクトとしても公開している。docs を変えた PR をマージしたら公開版も更新する。

依存の向き

flowchart TB
  web["apps/web"] --> core["packages/core"]
  runner["apps/runner"] --> core
  cli["apps/cli"] --> core
  web --> bundle["packages/bundle"]
  runner --> bundle
  cli --> bundle
  bundle --> core
  web --> db["packages/db"]
  runner --> db
  core --> db
  web -. "service binding / Queue のみ" .-> runner
  cli -. "HTTP（/api/sync/v1）のみ" .-> web
  • packages/bundle と packages/core は CLI にも同梱するので、Node・Bun・Workers のどれでも動く純粋な TypeScript にする（packages/db の型だけを参照し、D1 には触らない）。
  • packages/core は Next.js・Workers の API に依存しない。D1（Drizzle）、R2、fetch は引数で受け取り、Node の vitest でテストできるようにする。
  • apps/web と apps/runner は互いの import をしない。やり取りは service binding（RPC）と Queue のメッセージ（型は packages/core/src/messages.ts）だけ。
