実装ガイド

INDX Watch をどう作るかのガイドです。コードを増やさないためのルール、フォルダ構成、主要コードの書き方、ローカル開発とデプロイの手順、M1〜M4 のロードマップをまとめます。仕様そのものは第 1 層（PRD 〜 AI ネイティブ設計）が正で、このページは「その仕様をどう実装するか」を決めます。

状態 ドラフト v0.1更新 2026-11-19関連 アーキテクチャ · データモデル · テスト対象の登録

コードを少なく保つ方針

INDX Watch は社内ツールです。機能の多さより、少人数（と Claude Code）で読み切れて直せることを優先します。次のルールは「迷ったらこちら」の既定値です。外れる場合は PR の説明に理由を書きます。

ルール具体的にやることやらないこと
1 画面 = 1 route画面 S01〜S11 はそれぞれ 1 つの page.tsx（Server Component）。データはページ内で Drizzle から直接読む画面ごとに API を作って fetch する構成。BFF 層の追加
更新は Server Actionsフォーム送信・状態変更・アサインは actions.ts の Server Action。成功後は revalidatePathUI から呼ぶための REST / GraphQL エンドポイント
API は外部連携だけRoute Handler は /api/github/webhook、/api/runner/*（ランナーからのコールバック）、/mcp の 3 系統だけ内部用の汎用 API。/api/projects のような CRUD 一式
状態管理ライブラリを入れないサーバーの状態は URL（searchParams）と DB に置く。クライアント状態は useState と useOptimistic までRedux / Zustand / React Query / SWR の導入
スキーマは 1 か所入力の zod スキーマは packages/core/src/domain に置き、フォームの検証・Server Action・MCP ツールの入力で同じものを使う画面ごとに型やバリデーションを書き直すこと
UI は shadcn/ui の最小セットButton / Input / Textarea / Select / Dialog / DropdownMenu / Tabs / Badge / Tooltip / Sonner（トースト）の 10 種から始める使う予定のないコンポーネントの一括追加。独自デザインシステムの構築
テーブルは自前の薄い部品components/data-table.tsx（列定義の配列 + 行の配列 → <table>）。ソート・絞り込みは searchParams でサーバー側TanStack Table などの重いテーブルライブラリ
長い処理はランナーへブラウザ実行・LLM 判定・AI 取り込みは Queue に投げて apps/runner の Workflow で処理するweb の Worker 内で数十秒かかる処理を同期実行すること
マネージド機能を先に探す認証は Cloudflare Access、ファイルは R2、再試行は Workflows、定期実行は Cron Triggersログイン画面・セッション管理・ジョブキューの自作
リアルタイムは後回し実行中の進捗は 3 秒間隔のポーリング（router.refresh()）で十分M1〜M3 での WebSocket / Durable Objects 導入

行数の予算

「少ないコード」を測れるように、M3 完了時点の目安を決めておきます。テストコードとマイグレーション SQL、shadcn/ui の生成コードは数えません。予算を 20% 超えたら、作り直しかドキュメントでの合意を検討します。

apps/web/app11 画面の page / actions / 画面固有コンポーネント（1 画面あたり 300〜500 行）4,500

合計10,700

依存の向き

apps/* → packages/core → packages/db の一方向だけ。packages/core は Next.js や Workers の API に依存させず、Node でもユニットテストできる純粋な TypeScript にします（D1 や R2 は引数で受け取る）。

コード例

実装の骨組みです。細部は実装時に詰めますが、境界（どこで認証し、どこで DB に触り、どこで判定するか）はここに合わせます。

Cloudflare Access の JWT 検証（middleware）

Access を通ったリクエストには Cf-Access-Jwt-Assertion ヘッダーが付きます。Worker 側でも必ず検証します（Access の設定ミスや直接アクセスへの備え）。

// apps/web/middleware.ts
import { NextResponse, type NextRequest } from "next/server";
import { createRemoteJWKSet, jwtVerify } from "jose";

const TEAM = process.env.CF_ACCESS_TEAM_DOMAIN!; // 例: indx.cloudflareaccess.com
const JWKS = createRemoteJWKSet(new URL(`https://${TEAM}/cdn-cgi/access/certs`));

export async function middleware(req: NextRequest) {
  // GitHub Webhook は Access をバイパスし、ルート側で HMAC を検証する
  if (req.nextUrl.pathname.startsWith("/api/github/webhook")) return NextResponse.next();

  const token = req.headers.get("cf-access-jwt-assertion");
  if (!token) return new NextResponse("Cloudflare Access を経由してアクセスしてください", { status: 401 });
  try {
    const { payload } = await jwtVerify(token, JWKS, {
      issuer: `https://${TEAM}`,
      audience: process.env.CF_ACCESS_AUD,
    });
    const headers = new Headers(req.headers);
    headers.set("x-watch-email", String(payload.email ?? payload.common_name)); // サービストークンは common_name
    return NextResponse.next({ request: { headers } });
  } catch {
    return new NextResponse("認証トークンを確認できませんでした。ページを再読み込みしてください", { status: 401 });
  }
}

export const config = { matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"] };
// apps/web/lib/auth.ts — メールで users と突き合わせる。初回アクセス時は tester で作成

}

Server Action で計画アイテムを更新する

入力は core の zod スキーマで検証し、変更は必ず activity_log に残します（履歴が全部残る原則）。

// apps/web/app/(app)/p/[key]/plans/[n]/actions.ts
"use server";
import { revalidatePath } from "next/cache";
import { planItemUpdateInput } from "@indx-watch/core/domain";

export async function updatePlanItem(projectKey: string, input: unknown) {
  const user = await requireRole(projectKey, ["admin", "manager"]);
  const data = planItemUpdateInput.parse(input); // { planItemId, assigneeId?, priority?, dueDate?, status? }
  const db = getDb();

  const before = await db.query.planItems.findFirst({ where: eq(planItems.id, data.planItemId) });
  if (!before) return { ok: false, error: "対象のテストが見つかりません。画面を再読み込みしてください" };

  await db.batch([
    db.update(planItems).set(pick(data, ["assigneeId", "priority", "dueDate", "status"]))
      .where(eq(planItems.id, data.planItemId)),
    db.insert(activityLog).values({
      id: newId("act"), projectId: before.projectId, actorId: user.id,
      action: "plan_item.update", targetType: "plan_item", targetId: before.id,
      diffJson: diff(before, data),
    }),
  ]);
  revalidatePath(`/p/${projectKey}/plans`);
  return { ok: true };
}

ランナーの Workflow 骨組み

1 回の実行（runs 1 行）を 1 つの Workflow インスタンスで処理します。各 step.do は失敗時に再試行され、完了した段は再実行されません。

// apps/runner/src/workflows/run.ts
import { WorkflowEntrypoint, type WorkflowEvent, type WorkflowStep } from "cloudflare:workers";
import { decide } from "@indx-watch/core/policy";

type Params = { runId: string };

export class RunWorkflow extends WorkflowEntrypoint<Env, Params> {
  async run(event: WorkflowEvent<Params>, step: WorkflowStep) {
    const { runId } = event.payload;

    const ctx = await step.do("load", () => loadRunContext(this.env, runId));    // TC 版・環境・フィクスチャ版を確定
    await step.do("prepare-fixtures", { retries: { limit: 3, delay: "10 seconds", backoff: "exponential" } },
      () => applyFixtures(this.env, ctx));                                       // リセット / シードフック
    await step.do("mark-running", () => setRunState(this.env, runId, "running"));

    const steps = await step.do("execute", { timeout: "15 minutes" },
      () => executeInBrowser(this.env, ctx));                                    // agent / script。証拠は R2 へ
    await step.do("mark-judging", () => setRunState(this.env, runId, "judging"));

    const judgements = await step.do("judge", () => runJudges(this.env, ctx, steps)); // assert / visual / llm
    const verdict = decide(judgements, ctx.testCaseVersion.decisionPolicy, { priority: ctx.testCase.priority });

    await step.do("finalize", () => finalizeRun(this.env, runId, verdict));      // runs.verdict と plan_items を更新
    await step.do("notify", () => notify(this.env, ctx, verdict));               // GitHub Check Run / 失敗時の Issue 案
  }
}

判定ポリシー decide()

判定ポリシーは純粋関数にして、core のユニットテストで全分岐を押さえます。ルールの意味は AI ネイティブ設計 が正です。

// packages/core/src/policy/decide.ts
export type JudgeKind = "assert" | "visual" | "llm" | "human";
export type Verdict = "pass" | "fail" | "blocked" | "skipped" | "needs_review";

export interface Judgement { judgeKind: JudgeKind; verdict: Verdict; confidence?: number; reason: string; }
export interface DecisionPolicy {
  llmMinConfidence: number;          // 既定 0.8
  visualMaxDiffRatio: number;        // 既定 0.02（2%）
  requireHumanFor: Priority[];       // 既定 ["P0"]
}
export interface Decision { verdict: Verdict; reasons: string[]; }

export function decide(js: Judgement[], policy: DecisionPolicy, ctx: { priority: Priority }): Decision {
  const human = js.findLast((j) => j.judgeKind === "human");
  if (human) return { verdict: human.verdict, reasons: [`人の判定: ${human.reason}`] };            // (4) 最優先
  if (js.some((j) => j.verdict === "blocked")) return { verdict: "blocked", reasons: ["前提が崩れて実行できませんでした"] };
  if (js.some((j) => j.judgeKind === "assert" && j.verdict === "fail")) return { verdict: "fail", reasons: ["決定的チェックが失敗"] }; // (1)
  if (js.some((j) => j.judgeKind === "visual" && j.verdict !== "pass")) return { verdict: "needs_review", reasons: ["画面差分が閾値を超えました"] }; // (2)
  const llm = js.filter((j) => j.judgeKind === "llm");
  if (llm.some((j) => (j.confidence ?? 0) < policy.llmMinConfidence)) return { verdict: "needs_review", reasons: ["AI 判定の信頼度が低い"] }; // (3)
  if (llm.some((j) => j.verdict === "fail")) return { verdict: "fail", reasons: ["AI 判定が失敗と判断"] };
  if (policy.requireHumanFor.includes(ctx.priority)) return { verdict: "needs_review", reasons: [`${ctx.priority} は人の確認が必須`] }; // (5)
  return { verdict: "pass", reasons: ["すべてのジャッジが合格"] };
}
// packages/core/src/policy/decide.test.ts
import { describe, expect, it } from "vitest";
import { decide } from "./decide";

const policy = { llmMinConfidence: 0.8, visualMaxDiffRatio: 0.02, requireHumanFor: ["P0"] as const };

describe("decide", () => {
  it("assert が 1 つでも fail なら、LLM が pass でも fail", () => {
    const r = decide([
      { judgeKind: "assert", verdict: "fail", reason: "合計金額が ¥4,500 ではない" },
      { judgeKind: "llm", verdict: "pass", confidence: 0.95, reason: "割引表示あり" },
    ], policy, { priority: "P1" });
    expect(r.verdict).toBe("fail");
  });

  it("LLM の信頼度 0.79 は needs_review", () => {
    const r = decide([{ judgeKind: "llm", verdict: "pass", confidence: 0.79, reason: "" }], policy, { priority: "P2" });
    expect(r.verdict).toBe("needs_review");
  });

  it("P0 は AI が全部 pass でも人の確認待ち（RUN-1033 のケース）", () => {
    const r = decide([{ judgeKind: "llm", verdict: "pass", confidence: 0.91, reason: "" }], policy, { priority: "P0" });
    expect(r.verdict).toBe("needs_review");
  });

  it("人の判定は常に最優先", () => {
    const r = decide([
      { judgeKind: "assert", verdict: "fail", reason: "" },
      { judgeKind: "human", verdict: "pass", reason: "表示文言の変更は仕様どおり（PR #482）" },
    ], policy, { priority: "P0" });
    expect(r.verdict).toBe("pass");
  });
});

コーディング規約

項目規約
命名DB のテーブル・カラムは snake_case（plan_items.assignee_id）、TypeScript は camelCase（Drizzle で対応付け）。ファイル名は kebab-case。React コンポーネントは PascalCase。識別子は英語、UI 文言とコメントは日本語
ID主キーは newId(prefix) で {prefix}_{ULID}。prefix は prj env rel dep feat uc ac tc tcv fx fxv plan pi run rs ev jd bl sch iss ais cmt act usr。表示キー（TC-128）はプロジェクト内連番 number から formatKey() で作り、URL には番号を使う（/p/SHOP/tc/128）
日付・時刻保存は UTC の ISO 8601 文字列（D1 は TEXT）。表示は常に JST（Asia/Tokyo）で 2026-11-18 14:05 形式。期限など日付だけの値は YYYY-MM-DD で保存
エラー表示Server Action は例外を投げず { ok: false, error: "何が起きたか。どうすればよいか" } を返す。画面はトースト（sonner）で表示。想定外の例外は error.tsx で「もう一度読み込む」ボタン付きで表示し、ログに request id を出す
権限すべての Server Action と Route Handler の先頭で requireRole()。guest はクエリ側でも assignee_id = 自分 の条件を必ず付ける（画面で隠すだけにしない）
履歴仕様・フィクスチャ・計画・判定を変える処理は同じ db.batch() で activity_log に書く。テストケースとフィクスチャは更新ではなく新バージョンの追加
AI 生成物origin = 'ai'、model、prompt_version を必ず記録。プロンプトは packages/core/src/llm/prompts/*.ts に置き、変更したら版を上げる
秘密情報D1 には access_secret_ref / secret_ref のような参照名だけ。値は Secrets Store から runner だけが読む。ログ・証拠・LLM 入力に秘密値を入れない（fill ツールはマスクして記録）
ログconsole.log(JSON.stringify({ level, msg, runId, projectKey, requestId })) の 1 行 JSON。Workers Logs で検索できる形にする。個人情報とトークンは出さない
テストpackages/core はユニットテスト必須（判定ポリシー・ジャッジ・ID・スキーマ）。web の画面は INDX Watch 自身に WATCH プロジェクトとして登録し、INDX Watch で E2E テストする（ドッグフーディング）。M1 の各画面の完了条件はそのまま WATCH のユースケースと完了条件になる

デプロイ

GitHub Actions から Cloudflare にデプロイします。main への push で本番、PR では型チェックとテストだけ実行します。

  1. CI（PR ごと）

    pnpm typecheck → pnpm lint → pnpm test → pnpm db:generate --check（スキーマとマイグレーションのずれ検出）

  2. D1 マイグレーション（main）

    wrangler d1 migrations apply indx_watch --remote。マイグレーションは追加のみ（列の削除・型変更は 2 段階: 新列追加 → 次のリリースで旧列削除）

  3. runner をデプロイ

    wrangler deploy -c apps/runner/wrangler.jsonc。web がサービスバインディングで参照するため先に出す

  4. web をデプロイ

    opennextjs-cloudflare build && opennextjs-cloudflare deploy

  5. スモーク

    INDX Watch 自身の WATCH プロジェクトのスモーク計画を API から起動し、P0 が pass でなければ Slack に通知

ロールバック

  • Worker: wrangler rollback で直前のバージョンに戻す（web と runner は個別に戻せる）。
  • D1: マイグレーションは追加のみにしているため、コードを戻しても旧コードは動く。データの誤更新は D1 の Time Travel（wrangler d1 time-travel restore）で時点復元する。復元前に必ず wrangler d1 export で現状を保存する。
  • R2: 証拠とフィクスチャ本体は上書きしない（バージョンごとに別キー）ので、ロールバック対象外。

Claude Code での進め方

実装の大半は Claude Code が行う前提です。人はドキュメントとレビューに時間を使います。

  1. AGENTS.md を正とする

    用語・ID・スタック・フォルダ構成・作業ルールは AGENTS.md が正。CLAUDE.md はそれを読み込むだけ。食い違いを見つけたら先に AGENTS.md を直す

  2. docs を先に更新する

    仕様が変わるときは、同じ PR の最初のコミットで docs/（画面なら docs/screens/ のモック、テーブルなら data-model.html）を更新し、次のコミットで実装する

  3. 1 PR = 1 画面（または 1 機能）

    例: 「S07 フィクスチャ管理」だけの PR。その画面の「この画面の完了条件」を PR 説明にチェックリストとして貼る

  4. ドッグフーディングで確認

    PR に対応する WATCH プロジェクトの TC を実行し、RUN のリンクを PR に貼る（M2 以降は Watch Agent に実行させる）
