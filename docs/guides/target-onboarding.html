GUIDE-02 · テスト対象の登録

テスト対象（自社アプリ）の登録ガイド

自社のアプリを INDX Watch でテストできる状態にする手順です。「どのリポジトリを・どの環境で・どうやって入って・どのデータで」テストするかを登録しておけば、テスターはマイタスクを開くだけで迷わずテストを始められます。

状態 ドラフト v0.1更新 2026-11-19対象 QA リード・エンジニア関連 S09 環境・アクセス · S07 フィクスチャ管理

このガイドの目的

テストが止まる原因の多くは、テストそのものではなく準備にあります。「staging の URL はどれ？」「ログインできない」「クーポンのテストデータがない」「前の人のデータが残っていて結果が変わる」。このガイドでは、これらを登録時に一度だけ解決します。

登録が終わった状態

  • プロジェクト（SHOP）が GitHub リポジトリ indxdev/indx-shop とつながっている
  • 環境（staging / uat / preview）ごとに URL・入り方・テストアカウントがそろっている
  • テストの前に環境を決まった状態に戻す手順（リセット / シード）がある
  • 機能・ユースケース・完了条件・テストケースが登録され、スモーク計画が自動で動く

テスターから見た状態

  • マイタスクの各テストに「環境を開く」ボタンがあり、押すとそのまま対象画面に入れる
  • ログイン情報・テストカード番号・使うデータがテスト手順の横に出ている
  • 「この環境の入り方」を読めば、VPN が要るか・誰に聞けばよいかが分かる

全体の流れ

上から順に進めます。1〜4 はエンジニア、5〜7 は QA リード（または PdM）が担当するのが基本です。SHOP の場合、合計で半日〜1 日が目安です。

  1. プロジェクトを作り、GitHub App をインストールする

    INDX Watch で「プロジェクトを追加」→ キー（英大文字 2〜6 文字。例 SHOP）、名前、リポジトリ（indxdev/indx-shop）を入力します。続けて GitHub の組織に INDX Watch の GitHub App をインストールし、対象リポジトリへのアクセスを許可します。これでデプロイメント・PR・リリースの通知が届くようになります。

    必要な権限: Contents（読み取り）、Pull requests（読み書き）、Deployments（読み取り）、Checks（読み書き）、Issues（読み書き）、Metadata（読み取り）。

  2. 環境を登録する（URL・入り方・アクセス方法）

    S09 環境・アクセス で環境を追加します。SHOP では staging（既定）、uat、preview の 3 つです。ベース URL、アクセス方法（cf_access / basic / ip_allowlist / none）、資格情報の参照名、入り方ガイドを入力します。必須項目は次の表を参照してください。

    preview は PR ごとに URL が変わるため、URL を https://pr-{pr_number}.shop.example.com のようにテンプレートで登録します。GitHub の deployment_status に URL が含まれていればそちらが優先されます。

  3. テストアカウントとフィクスチャを登録する

    S07 フィクスチャ管理 で、テストに必要なデータを種類ごとに登録します。パスワードなどの秘密値は INDX Watch の画面から Secrets Store に保存され、D1 には参照名だけが残ります。

    種類SHOP での例中身
    accountFX-11 staging 会員アカウントメールアドレス・パスワード（秘密値）・会員ランク。環境 staging に限定
    datasetFX-3 クーポンセット（CSV, v4）クーポンコード・割引額・有効期限。テストケースのパラメータとして使う
    datasetFX-9 テスト用クレジットカード決済サンドボックスのカード番号・有効期限・期待結果（成功 / 拒否）
    seedFX-7 ゲスト購入用の在庫テスト前に投入する商品と在庫数。シード API に渡す JSON
    fileFX-14 返品用の商品画像アップロード操作で使う画像ファイル

  4. リセット / シードの手順を定義する

    環境ごとに「テスト前に決まった状態へ戻す方法」を reset_hook_json として登録します。対象アプリにテスト用 API があれば、ランナーが実行前に自動で呼びます。API がない環境では、手動の手順（例: 管理画面で注文を削除）を入り方ガイドに書き、テストケースの前提条件にリンクします。

    {
  "reset": { "method": "POST", "path": "/__test/reset", "timeoutSec": 60 },
  "seed":  { "method": "POST", "path": "/__test/seed",  "timeoutSec": 60 },
  "auth":  { "kind": "cf_access_service_token", "secretRef": "SHOP_STAGING_ACCESS" },
  "runBefore": "each_run"
}

  5. 機能・ユースケース・完了条件を登録する（AI 取り込み可）

    S03 仕様ツリー に機能 → ユースケース → 完了条件の順で登録します。既存の PRD や仕様書、Notion のページがあれば S10 AI 仕様取り込み に貼り付けると、AI が下書き（draft）を作ります。下書きは人が確認して承認するまで正式な仕様になりません。

    例: FEAT-3 カート・決済 → UC-12 ゲストがクーポンを適用して購入する → AC-12.1 有効なクーポンを入れると割引額が注文合計に反映される

  6. テストケースを作る

    完了条件ごとに、それを確かめるテストケースを作ります（S04 テストケース詳細・編集）。手順は平易な日本語で書き、使うフィクスチャと実行モード（manual / agent / script / hybrid）、優先度を設定します。完了条件のうちテストケースがないものは、仕様ツリーで「未カバー」と表示されます。

    例: TC-128 有効クーポンで割引が反映される（P0、agent、FX-3 と FX-7 を使用）

  7. スモーク計画と自動実行を設定する

    デプロイのたびに必ず確認したいテスト（ログイン・検索・購入など）に smoke タグを付け、スモーク計画を作ります。「staging へのデプロイ成功時に実行」を有効にすると、GitHub の deployment_status を受けて Watch Agent が自動で実行し、結果が PR の Check Run に表示されます。夜間に全件流す場合は定期実行（cron）を設定します。

  8. 動作確認する

    動作確認チェックリスト を上から確認します。すべて通れば、テスト計画を作ってテスターにアサインできます。

入り方ガイドの書き方

入り方ガイド（entry_guide_md）は、テスト手順の横と環境ページに表示される短い Markdown です。読む人はビジネス職や顧客かもしれません。専門用語を避け、「上から読めば入れる」順序で書きます。

書くこと

  • 開く URL と、最初に表示される画面
  • ログイン方法（どのテストアカウントを使うか。パスワードは書かず「右の『ログイン情報』を表示」と案内）
  • VPN や社内ネットワークが要るか
  • テストカード・クーポンなど、使うデータの場所
  • やってはいけないこと（本物のカード番号・個人情報を入れない など）
  • 困ったときの連絡先

書かないこと

  • パスワード・トークンなどの秘密値（Secrets Store に置き、画面からは権限のある人だけが表示できる）
  • テストケース固有の手順（テストケース側に書く）
  • アプリの仕様説明（仕様ツリーに書く）

テンプレート（SHOP staging の例）

## staging の入り方

1. 「環境を開く」を押すと https://staging.shop.example.com が開きます。
   社内アカウントで Cloudflare のログイン画面が出たら、会社のメールアドレスでログインしてください。
   VPN は不要です。
2. 会員としてテストする場合は、右側の「ログイン情報」から FX-11（staging 会員アカウント）を表示し、
   画面右上の「ログイン」から入ってください。ゲストのテストではログインしません。
3. 決済では、本物のカードは使えません。FX-9（テスト用クレジットカード）の番号を使ってください。
   例: 4242 4242 4242 4242 は「成功」、4000 0000 0000 0002 は「拒否」になります。
4. クーポンコードは FX-3（クーポンセット）にあります。期限切れ用のコードも入っています。

### 注意
- staging は毎日 5:00（JST）にデータが初期化されます。前日に作った注文は残りません。
- 注文確認メールは実際には送られません。テスト手順の「メールを確認」から受信内容を見られます。
- 個人情報（本名・本物の住所）は入力しないでください。

### 困ったとき
Slack #shop-dev（担当: 鈴木 翔）

対象アプリ側に用意するもの

AI エージェントやスクリプトで安定してテストするには、対象アプリ側の協力が必要です。下の 4 つを staging / uat に用意してもらいます。どれも本番環境では無効にしてください。

1. テスト用のリセット / シード API

実行のたびに環境を同じ状態に戻すための API です。INDX Watch のランナーは Cloudflare Access のサービストークン（CF-Access-Client-Id / CF-Access-Client-Secret ヘッダー）を付けて呼びます。アプリ側は Access を通過したリクエストだけを受け付けてください。

APIリクエストレスポンス決まりごと
POST /__test/reset{ "scope": "all" | "orders" | "carts", "runId": "run_01J..." }200 { "ok": true, "resetAt": "2026-11-18T05:00:00Z" }冪等であること。60 秒以内に返ること。テストアカウント（FX-11）は消さない
POST /__test/seed{ "fixture": "FX-7", "version": 3, "data": { ... }, "runId": "..." }200 { "ok": true, "created": { "products": 3, "stock": 30 } }data はフィクスチャ本体（seed の JSON）。同じ内容を 2 回送っても重複しない（upsert）
GET /__test/healthなし200 { "ok": true, "commit": "a1b2c3d" }デプロイされているコミットを返す。実行前の確認と、デプロイメントの突き合わせに使う
 
// seed の data の例（FX-7 ゲスト購入用の在庫 v3）
{
  "products": [
    { "sku": "TEST-TSHIRT-M", "name": "テスト用 Tシャツ M", "price": 3000, "stock": 10 },
    { "sku": "TEST-MUG",      "name": "テスト用マグカップ",  "price": 1500, "stock": 10 },
    { "sku": "TEST-CAP",      "name": "テスト用キャップ",    "price": 2500, "stock": 10 }
  ]
}

2. data-testid の付与方針

AI エージェントは画面の見た目とアクセシビリティ情報（ボタン名・ラベル）で操作するため、data-testid がなくても動きます。ただし script モードと assert ジャッジの安定性のため、次の要素には付けてください。

  • 主要な操作ボタン: data-testid="checkout-submit"、"coupon-apply"
  • 検証に使う値の表示: "order-total"、"discount-amount"、"coupon-error"
  • フォーム入力: "coupon-code"、"card-number"
  • 命名は {画面や領域}-{要素} の kebab-case。表示文言を変えても変えない。1 画面内で一意
  • ボタンやフォームには見えるラベル（または aria-label）を必ず付ける。エージェントと人の両方が迷わなくなる

3. メール受信の確認方法

「注文確認メールが届く」（AC-12.3）のような完了条件を確かめるため、staging のメールを外部に送らず、テスト用メールボックスで受け取れるようにします。

API内容
GET /__test/mailbox?to=guest+{runId}@test.shop.example.com宛先ごとの受信メール一覧（件名・本文テキスト・受信時刻）。新しい順
DELETE /__test/mailbox?to=...受信メールの削除（reset でまとめて消えるなら不要）

宛先に runId を含めると、同時に動く別の実行のメールと混ざりません。メールボックス API を用意できない場合は、Mailpit などのテスト用 SMTP サーバーの API を同じ形で公開してもらいます。

4. 外部決済のサンドボックス

  • staging / uat の決済は、決済サービスのテストモード（サンドボックス）に接続する。本番の API キーを置かない。
  • 成功・拒否・3D セキュア要求など、結果ごとのテストカード番号を FX-9 テスト用クレジットカードに登録する。
  • 3D セキュアの認証画面など外部ドメインに遷移する場合は、そのドメインを入り方ガイドに書く（エージェントの移動許可リストにも使う）。

設定ファイル .indx-watch/project.yaml（任意）

DB が正です

プロジェクトの設定は INDX Watch のデータベースが唯一の正です。このファイルは「最初の登録をまとめて行う」ためと「環境や自動実行の設定変更を PR でレビューする」ためのインポート元です。ファイルを変更して main にマージすると、GitHub App が差分を検出して S09 に「設定ファイルからの変更案」を出し、管理者が承認したときだけ反映されます。DB 側で直接変えた内容がファイルに書き戻されることはありません。

# .indx-watch/project.yaml（indxdev/indx-shop リポジトリ）
project:
  key: SHOP
  name: INDX Shop（サンプル）

environments:
  - name: staging
    kind: staging
    default: true
    base_url: https://staging.shop.example.com
    access: { kind: cf_access, secret_ref: SHOP_STAGING_ACCESS }
    reset_hook:
      reset: { method: POST, path: /__test/reset }
      seed:  { method: POST, path: /__test/seed }
      run_before: each_run
    entry_guide: ./entry/staging.md          # 入り方ガイド（Markdown）
  - name: uat
    kind: uat
    base_url: https://uat.shop.example.com
    access: { kind: cf_access, secret_ref: SHOP_UAT_ACCESS }
    entry_guide: ./entry/uat.md
  - name: preview
    kind: preview
    base_url: https://pr-{pr_number}.shop.example.com
    access: { kind: cf_access, secret_ref: SHOP_STAGING_ACCESS }

automation:
  smoke:
    tags: [smoke]                  # このタグの付いた ready のテストケースが対象
    on_deployment: [staging, preview]
    environment_from_deployment: true
  nightly:
    cron: "0 18 * * *"             # UTC。JST 3:00
    environment: staging
    selector: { priority: [P0, P1] }

notifications:
  github_checks: true              # PR に Check Run を付ける
  failed_run_issue: suggest        # 失敗時に Issue 案を作る（suggest / auto / off）
  slack_channel: "#shop-qa"

秘密値はこのファイルにも書きません。secret_ref の参照名だけを書きます。

顧客 UAT 環境を開く

顧客（例: 株式会社サンプルの山本様）に受け入れテストをしてもらう手順です。顧客は guest ロールで、自分にアサインされたテストだけが見えます。

  1. uat 環境を用意する

    エンジニアが uat 環境（https://uat.shop.example.com）にリリース候補をデプロイし、S09 で uat の入り方ガイドを顧客向けの言葉で書く。社内用語や Slack チャンネル名は入れず、問い合わせ先は QA リード（佐藤 美咲）のメールにする

  2. Cloudflare Access で招待する

    インフラ担当が INDX Watch と uat 環境の両方の Access アプリケーションに、顧客のメールアドレスを許可ポリシー（ワンタイム PIN）として追加する。社外ドメインはメールアドレス単位で許可し、ドメイン全体は許可しない

  3. INDX Watch にゲストを追加する

    管理者が SHOP の メンバーに顧客のメールアドレスを guest で追加する。初回ログイン時にメールアドレスで突き合わされる

  4. UAT 用のテスト計画を作ってアサインする

    QA リードが「v2.4.0 受け入れテスト」計画を作り、環境 uat、担当 山本様で TC をアサインする。手順はビジネス職が読める表現になっているか、事前に高橋 由佳（PdM）が確認する

  5. 案内を送る

    INDX Watch の URL、ワンタイム PIN でのログイン方法、期限を顧客に連絡する。顧客がログインするとマイタスクに UAT 項目だけが並ぶ

  6. 終わったらアクセスを外す

    UAT 完了後、Access の許可ポリシーから顧客を外す（または期限付きで設定しておく）。INDX Watch 上の実行結果と証拠は残る

動作確認チェックリスト

登録が終わったら、QA リードが次の項目を確認します。すべて満たせば、テスト計画を作ってアサインを始められます。

入り方ガイドだけで入れるプロジェクトに初めて参加する人（例: 高橋 由佳）に S01 から 1 件実行してもらう人に聞かずに環境に入り、ステップを記録できる
完了条件が網羅されているS03 で「未カバー」フィルタP0 / P1 のユースケースに未カバーの完了条件がない

よくあるつまずき

症状よくある原因対処
エージェントが Cloudflare のログイン画面で止まるサービストークンが対象環境の Access ポリシーに入っていない、または参照名の誤りAccess アプリに「Service Auth」ポリシーを追加し、S09 の access_secret_ref と Secrets Store の名前を一致させる
人は入れるがエージェントだけ 403対象アプリが IP 制限をしているaccess_kind を cf_access に寄せる。IP 制限が必須なら Browser Rendering の送信元を許可する方法をインフラ担当と決める
